# Стандартный и расширенный сервисы загрузки программы

Уточнение: [XML моделей и отдельные сервисы 3 и 532](omron-cj1-service-xml.md).
Значение DriverReleaseVersion не следует трактовать как firmware ПЛК.

Статическое исследование 17 ноября 2026 года, после `0b4f5cde`.
ПЛК не опрашивались, vendor API не выполнялись. Действующая установка остаётся
только чтение, `.36` offline.

## Существенное различие команд

В `CXSDI_SeriesCS1MessageServices1.dll` найдены разные реализации:

| Сервис | Транзакция | Кодировщик | Команда |
| --- | --- | --- | --- |
| ProgramDownloadServiceCS1Common | CDownloadProgramTransaction | 63019140 | 0307 |
| ProgramDownloadExServiceCS1H_V4Common | CDownloadProgramExTransaction | 630188f0 | 0317 |

В расширенном кодировщике по адресам `63018a09`/`63018a0c` записываются
непосредственно bytes `03` и `17`. Оба варианта используют номер программы,
32-bit смещение, длину и last-bit `8000`; это не делает их взаимозаменяемыми.
Сравнение assembly также не показало побайтной идентичности функций: 207 и
210 инструкций, разные служебные участки. Семантику `0317` и ограничения
физического CPU нельзя выводить только из сходства полей.

Конструкторы обычного `63030ae0` и расширенного `6302f710` сервисов создают по
две транзакции. Вторая различается: `63019090` против `63018840`.
Версия сервиса, реально выбираемая для CJ1H/CPU65 и CJ1M/CPU21, ещё **не установлена**.
Название класса `V4` не приравнивается автоматически к версии firmware ПЛК.

В offline-планировщике `0307` теперь явно указана эта неопределённость в
`Unresolved`. Автоматического переключения на `0317` нет. Добавлен тест,
подтверждающий, что проверка ACK `0307` отклоняет ответ с командой `0317`.
`WriteQualified` и `WireImageMappingQualified` остаются false.

## Предварительное состояние и чтение исходного файла

Первая транзакция обоих сервисов создаётся через `630380e0`. Точное RTTI-имя
по `63060210` — `CReadStatusTransaction`. Предварительное предположение о
`CGeneralReadCommonTransaction` из похожих имён других библиотек было неверным;
на него не следует опираться в дальнейшей трассировке.

При этом `CReadStatusTransaction` действительно участвует в подготовке файла:

- `630383d0` проверяет внутренний тип запроса `9` и вызывает формирование
  предварительной команды состояния;
- базовый `630375a0` разбирает возвращённое состояние;
- `630385e0` вызывает базовый разбор, затем открывает исходный файл через
  `ifstream`, читает его по byte в собственный буфер и закрывает файл;
- ошибка открытия/слишком короткий файл дают `2006`; далее проверяется размер
  относительно параметров области UM, включая различие WORD/других единиц;
- на успешной ветви формируется внутренний результат с длиной прочитанного
  файла, а не сетевой `0307`/`0317` пакет.

В этом фрагменте нет найденного пересчёта checksum/header0/1/4. Это наблюдение
об исследованной функции, **не доказательство** отсутствия преобразования
образа во всём workflow. Окончательная передача буфера во вторую транзакцию,
полная ветвь ошибок и подготовка service fields требуют продолжения анализа.
Различие real-UM `ceil(bytes/64)` и resident quantum `256` не закрыто.

## Откуда берётся версия сервиса

`ParallelCommunication::Initialise:61a0cfa0` создаёт генератор через
`61a13580`. Он получает данные из интерфейса DeviceInfo и обходит XML-описания
с XPath вида:

```text
%Network%/Services/Services[@Name='Local']/Service
%Network%/Services/Services[@Name='Remote']/Service
```

Подтверждены встроенные wide strings атрибутов `CommandNo`, `DllPath`,
`ClassName`, `SuperClassName`, `SupportVersion`. В коде есть разбор значения
`SupportVersion`; точная привязка этих значений к модели и фактической версии
контроллера не установлена.

В `61a13470` выбранная числовая версия — максимальная из доступных, не выше
переданного ограничения; исходное значение поиска равно `0`. Затем используется
таблица версий. Это правило само по себе ещё не объясняет источник ограничения
для конкретного CJ1 и поведение всех случаев без подходящей записи.

`61a12fb0` передаёт выбранные DLL/class/superclass в
`ClassLoaderCore::CreateInstance:62e01f90` из `CXSDI_PlainLib.dll`. Последний
использует `LoadLibraryA`/`GetProcAddress` для выбранной фабрики. Эти функции
исследовались статически; библиотеки не загружались нами для исполнения.
Сам загрузчик не определяет версию CPU.

Поиск только в registry Omron не нашёл строк `ProgramDownload*`; это не
доказательство отсутствия метаданных. Выбор идёт через XML DeviceInfo, и его
конкретный экземпляр ещё предстоит извлечь из поставщика данных.

## Проверка и воспроизводимость

Raw Ghidra JSON, pseudo-C, PE imports, сравнение кодировщиков, проверочный
`verify-selection.py` и manifest находятся вне Git в
`research/hardware/20261117-cj1-service-selection-01`.
Статическая сверка дала **28/28**: source hashes, состав транзакций, точное RTTI,
opcode `0317`, last-bit, чтение файла и metadata strings.
Manifest включает 50 файлов, SHA-256:
`7f0b81e0016a8f2450f64832d0cae9c88958ad2844b0bc35b292f5e4ec55d8bb`.

Проверки кода: `go test ./omron/transfer -count=1`, Omron CLI tests,
`go vet ./omron/transfer`, сборка Nautilus — прошли. Тест ACK синтетический;
реальных ответов записи на ПЛК не получали.

Основные входы:

завершения на соответствующем CPU. Аппаратная запись по-прежнему не разрешена.
