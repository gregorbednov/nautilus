## Layout функции12685840

Writer открывает исходный файл на чтение и новый файл с create/write.
При descriptor+44 &0x3c ==0 эта ветвь вообще не выполняется.
В остальных случаях базовый префикс определяется bit20 того же descriptor:

| Ветка | Префикс | Word1 при IsExtendedProtect !=0 | Затем |
| --- | --- | --- | --- |
| bit20 сброшен |48 bytes, первоначально нулевые | big-endian0x80 по offset4 | optional380 bytes, затем весь исходный файл |
| bit20 установлен |256 bytes с CJ2X/CJ2M magic и дополнительными полями | big-endian0x81 по offset4 | optional380 bytes, затем весь исходный файл |

Обычная48-byte ветвь явно обнуляет12 dwords (`126859f8…12685a05`) и передаёт
48 bytes в CFile::Write (`12685a4a/12685a50`). При включённом флаге
`12685a2b` задаёт800000 и `_swab` превращает это в bytes `00 00 00 80`;
они сохраняются в word1 префикса. В256-byte ветви аналогично получается81.

При включённой защите writer получает две строки через124b99a0/124abef0,
выделяет380 bytes и вызывает1284f050. Далее читает первые24 bytes исходного
файла и вызывает1284f620, после чего **12685b67 записывает ровно0x17c bytes**.
Значения строк не извлекались; генератор защищённого блока не исполнялся.

После префикса и optional блока writer снова ищет **начало исходного файла**,
получает полную длину и копирует его целиком блоками до65536 bytes.
Поэтому для обычного случая результат:

```text
[48 zero bytes] [полный N1 без изменений]
```

При включённой защите в этой вызывающей ветви исходный файл до копирования
проходит отдельный helper126994d0/EncryptUMObject. Его порядок ошибок/UI
не переносится в независимый код.

Это разрешает прежнее противоречие: offset4, который читает12694ab0, относится
к **локальному префиксу**, а не к word1 сырого N1/UM. Служебная сумма readback
расположена в самом теле N1. Нельзя читать её как marker80/81.

## Что реализовано в Go

`omron/um/object.go`:

- `WrapPlainN1Object(n1)` сначала проверяет N1, затем создаёт48 нулевых bytes
  и копирует тело без изменения service sums/flags/кода;
- `ParsePlainN1Object(data)` требует именно нулевой48-byte префикс и корректный
  полный N1 после него; возвращает N1Image с собственными байтами;
- `ErrPlainN1ObjectLayout` отличает неподдержанный контейнер, ошибка тела также
  сохраняет ErrN1Layout для errors.Is;
- размер тела ограничен существующим MaxSize. Защита, CJ2, непустой prefix,
  повреждённое тело и appended metadata отвергаются.

Это намеренно узкий локальный формат. API не выбирают active service,
не меняют защиту/режим и не отправляют байты. CLI-команды для этих API ещё
не подключены. Результат Wrap — контейнер файла, **не payload0307**;
для сырого N1 остаётся ParseN1. Hardware/write qualification не появилась.

Нового native OBJ-образца нет: тестовые контейнеры построены по подтверждённой
структуре writer вокруг двух закреплённых compiler N1. Это ограничение
сохраняется, несмотря на точное совпадение тела и подтверждённые инструкции.
