# Нативная арифметика UM и финализация последнего блока

Исследование16–17 ноября2026 года. Пользователь подтвердил продолжение
исследования. Действующая установка остаётся **только чтение**, отключение
исполнительных механизмов не объявлено. В этом этапе вообще не было сетевых
обращений к ПЛК; `.36` offline и не опрашивался.

## Новый результат для сохранённого проекта CJ1H

Для ранее независимо скомпилированного неизменённого CXP CJ1H взята **копия**
4604-byte файла с нулевыми начальными6 словами. В этой исследовательской копии
заполнены только0/1/4 по наблюдаемым формулам:

```text
S = sum(big-endian uint32 words[6:]) modulo 2^32
word0 = S & 0xffff
word1 = S >> 16
word4 = ceil(image byte length / 64)
```

Полученный файл **побайтно целиком совпал** с4604-byte UM, считанным после
ручной загрузки этого CXP через CX-One. SHA-256 обоих:
`3d4c2e0781600e0219dcef9713aa6a4fcdc33d750b1a85140382ad5e3f901cf3`.
Исходный Go compiler file имеет SHA-256
`05c6fede7156d53eaafb2173726c8af26f7963cee2a4cd54d1d1ceb2f35ef4bf`;
он не изменён. Новый файл на ПЛК не передавался.

Это точное воспроизведение **конкретного исторического образа** из CXP и
явных JSON настроек, не универсальная спецификация загрузки. Текущая программа
`.37` в предыдущем чтении была2716-byte учебным примером. Его изменение
этой проверкой не предполагается. Автоматического заполнения заголовка в
продуктовом компиляторе/планировщике не добавлено.

Добавлены диагностические `blocks64FromImageLength` и
`storedBlockCountMatches` в `N1Image.ServiceFields()`. Исходные bytes не меняются.
Это наблюдаемая зависимость. Четырёх длин недостаточно для квалификации всех
границ: в частности, влияние исключённых24-byte служебных данных и padding
на иных длинах не установлено. Поля2/3/5 остаются неинтерпретированными.

Ghidra12.1.4 сохраняет assembly, вызовы, pseudocode и input hashes. Таблица
CS2 найдена через dispatcher10011ea0, group3 root1002dccc, entry0307
1002ce20→1000b790. Для plain варианта root10028178 подтверждён dispatcher
1000da40; entry10027958→100057f0. Это прослеженные командные таблицы,
а не предположение из похожего имени функции.

В обоих обработчиках0307 после проверки параметров данные копируются в UM.
Только установленный last-block bit вызывает final routine. Ответ переносит
номер/адрес/длину, причём count маскируется7fff. Финализация обнуляет неиспользованный
хвост, считает32-bit сумму после первых24 bytes и записывает low/high16
в header offsets0/4; отдельная функция заполняет offset10 hex (word4).
В plain варианте длина берётся из20-bit поля по offset80 hex — знакомого
N1 total-word-count. CS2 использует другую схему смещений заголовка.

Это показывает, что исследованный **виртуальный CPU сам формирует служебные
поля при завершении записи**. Не доказано, что реальный CJ1M/CJ1H выполняет
в точности тот же путь и принимает те же входные значения. Сам handler,
финализация и симулятор в этом этапе не исполнялись.

Craft evidence: arithmetic dossier
`ev_864ec28ef60a8cd0610ee63a45d5c5f5c16f20f4faf6819ffed7ad35a6b1b0c3`,
plain finalization dossier
`ev_342856ba4bbb8a02541776c559321b0cec9f6862892c510e7f7101a5e26101b4`.

## Независимая проверка чистого сумматора

`subcb_sum_make` в двух DLL побайтно одинаков:100 bytes, SHA-256
`0d993a5edc6d751a13abdc80dc6440992ee1811365d5af873d1b7fb11e3e3f99`.
У функции нет внешних вызовов или глобальных данных: она только читает
переданный буфер и складывает8/16/32-bit значения. Режим2 —32-bit сумма.

Проверенные100 bytes выполнены в отдельном x86-процессе на собственных
ограниченных буферах, без загрузки vendor DLL. Код и source hashes закреплены
в worker; исполняемая область после копирования read/execute. Нет адреса ПЛК,
импорта транспорта или вызова FINS. Первичная ошибка marshaling UIntPtr
исправлена до успешного исполнения тестов; все результаты получены повторно
с проверкой фиксированного code hash.

Все80 случаев совпали:76 synthetic (включая нулевые/отрицательные длины,
неполные элементы, переполнение суммы) и4 тела аппаратных UM. На Linux и
других платформах Go replay использует записанные результаты:38 synthetic
32-bit случаев проверяют рабочий Go accumulator после явного LE↔BE перевода
числовых контейнеров. Остальные режимы не выдаются за новые возможности N1.

Переносимый корпус: `omron/um/testdata/native-um-sum-*` и
`native-um-service-observations.json.gz`. Manifest закрепляет input/module/code
hashes и compressed/decoded hashes. Полные аппаратные UM в Git не добавлены.

## Конкретный незакрытый вопрос

Нативные функции контроля обходят resident UM блоками256 bytes, а обе
исследованные final-count функции10011620/1000d240 вычисляют
`ceil((residentEnd-residentBase)/256)`. Реальные прочитанные поля соответствуют
64-byte формуле из таблицы выше. Причина различия и отображение resident
представления/семейства CPU на фактический wire image **не установлены**.
Одинаковый arithmetic helper этого различия не устраняет.

Поэтому нельзя автоматически перенести финализацию виртуального CPU в
загрузчик CJ1. `nativeAlgorithmConfirmed` в API продолжает означать полную
квалификацию target format/stamping и остаётся false; арифметика проверена
отдельно. `writeQualified` также false. В offline плане причина дополнена
явным различием256/64; автоматического переписывания headers нет.

Следующее: установить выбранную CPU-модель и преобразования resident↔wire,
разобрать подготовку отправителя CX-One, затем воспроизвести ответы/отказы и
завершение0307 на имитаторе. Проверка реальной финализации требует отдельного
разрешённого стенда с деактивированными механизмами и восстановлением.
Нынешнее подтверждение исследования не использовано как разрешение на запись.
