# CJ1: UseDefault и происхождение стека компилятора

Продолжение: [BR2/default profile](omron-cj1-br2-and-fb-profile.md) уточняет,
что ветка init проверяет поддержку FB независимо от сохранённого UseFB-флага,
и показывает разные источники версии. BR2 получает только default-кандидат.

18 ноября 2026 года. Уточнение [аудита CXP](omron-cj1-source-settings-audit.md).
Статический разбор объясняет, почему сохранённый D0 нельзя было считать
безусловным конфликтом с AC0. Старые снимки не менялись; классификация аудита
исправлена на основании новой цепочки инструкций.

## Подтверждённая цепочка

Бинарные сборки: CX-P.exe SHA-256
`e91f15b8613e56c8f326bc83ce07f5a24b177f5f70a4a445e4eadfa34b0a9eb4`,
CX-Pdata.dll SHA-256
`a32ada50d87bc39697ca7c57337b8e64b14e59bca54d54791929cbe7db678141`.
Ghidra 12.1.4, выбранные функции, без общего auto-analysis; проекты открывались
read-only. Vendor-код, CX-One и ПЛК не запускались/не вызывались.

| Путь | Проверенный факт |
| --- | --- |
| 126173d0 | Конструктор stack-object выставляет byte+8 в 1 |
| 12617720 | Читатель UseDefault записывает byte+8; default=1, поле необязательно |
| 12617630 | Writer опускает UseDefault при значении 1; остальные поля сохраняются независимо |
| 12617720 | WordSize читается в +2c, BitSize в +30; строки имён сверены в PE |
| 12439de0 | FBMemory читает вложенный StackSettings и копирует в свой объект |
| 1243aa00 → 126175f0 | Мост копирует объект из FBMemory+30c, включая flag+8 и размеры+2c/+30 |
| 124b9be0 | Сначала вызывает InitialiseBaseRegisters, затем проверяет скопированный flag |
| 124b9cfb..124b9d01 | Ненулевой flag пропускает SetStackRegister |
| 124b9d11..124b9d46 | При false передаёт BitSize и WordSize+BitSize |
| 121ce7e9 | На поддержанной ветке InitialiseBaseRegisters использует таблицу 122a6b78 |
| 122a6b78 | Три DWORD: указатель на AC0, 0x40, 0x600 — AC0/64/1536 |

Импорты подтверждены через IAT: thunk1285ab26 → InitialiseBaseRegisters,
thunk1285ab1a → SetStackRegister, thunk1285ab20 → SetBaseRegister.
В asm формула размеров проверена по локальным смещениям: stack-object находится
на ESP+20, WordSize — ESP+4c, BitSize — ESP+50. EAX получает BitSize, ECX —
WordSize, EBP — сумму; далее PUSH EBP, PUSH ESI(BitSize), PUSH address.
Неверные типы параметров в псевдокоде не использованы как самостоятельное
доказательство ABI или порядка аргументов.

## Что меняется для настоящих CXP

Во всех четырёх проектах StackSettings присутствует, UseDefault отсутствует.
Сохранённые D0/1472/64 не активируют явный setter. Изученная ветка оставляет
инициализированный стек; её таблица соответствует AC0/64/1536 из рецепта.
Это объяснение статического пути, не новый запуск CXP в native-компиляторе.
Полнота выбора профиля, UseFB/feature predicate и все пути загрузки resource
не объявляются доказанными. Native default ранее наблюдался на двух контекстах,
но новое исследование не удостоверяет конкретную unit version реального CPU.

`audit-image-settings` теперь выводит `stackSelection`, `stackSelectionOrigin`
и `stackCallCandidate`. Если StackSettings есть, отсутствующий UseDefault
получает только этот подтверждённый default. Остальные отсутствующие поля,
включая BR2, по-прежнему не заполняются. Без самого StackSettings выбор unknown.

Для use-default проверка stack-address стала unverified с пояснением, что
сохранённый адрес не применяется. stack-default-table проверяет равенство
рецепта закреплённой таблице; passed относится к таблице, не к активации ветки.
Кандидат AC0/64/1536 — диагностика этой ветки, не автоматически выбранный профиль.

Для явного UseDefault=false/0 аудит сравнивает сохранённый адрес, а
stack-call-arguments — BitSize/WordSize+BitSize. Например, D0/1472/64 даёт
D0/64/1536 и отличается от AC0-рецепта адресом. Аудит принимает только ограниченные
целые неотрицательные размеры; неподдержанный набор не получает подтверждения.
Значения true/false проверяются без учёта регистра, 1/0 поддержаны как в reader.
Неизвестное или quoted-значение отвергается без отчёта.

Общая квалификация sourceSettingsVerified/storageInitialized/globalStorageAudited/
hardwareQualified/writeQualified остаётся false. Инициализация данных, профиль
CPU и BR2 не выводятся из одного совпадения стека. Генератор N1 и явные настройки
сборки не переписываются; поведение настоящего PLC не меняется.

## Воспроизведение и границы доказательства

Корпус `omron/compiler/testdata/stack-source-origin.json.gz`: 15 функций,
SHA-256 `8c546677e69507ec3aa533161d4408a86d9a75541d9fd8d2693401ac5f979185`.
`verify_cj1_stack_origin.py` проверяет фиксированные 29 asm checkpoints, сведения
о функциях/сборках и согласованность инструкций. С опциональными --cxp/--pdata
дополнительно проверяются SHA-256, строки, IAT и реальные bytes default-table.
Полная локальная проверка дала 1496 checks. Это не новый дизассемблер и не
доказательство полноты всех вызывающих путей.

```sh
python -B tools/omron-research/verify_cj1_stack_origin.py omron/compiler/testdata/stack-source-origin.json.gz --output NEW-REPORT.json
```

Три Python-теста проходят без vendor binaries, включая отказ при изменении
каждого из 29 checkpoints, другой сборке и повышении qualification-флагов.
Прошли тесты всех 10 Omron-пакетов, Omron CLI и vet. Отдельно проверены четыре
настоящих CXP и пять синтетических вариантов UseDefault/адреса/размеров.
Для отдельных запусков использовался NAUTILUS_CLI=1 (принудительный CLI,
обход предварительного поиска встроенного проекта). Без него запуск дважды
превысил 30/120 секунд без вывода; причина задержки окончательно не установлена.
Проверки завершились с этим явным режимом; тайм-ауты сохранены как ограничение
отдельного запуска, а не скрыты под результатом тестов.
Материалы: `research/hardware/20261118-cj1-stack-origin-01`, с командами,
Ghidra JSON/logs, исходниками, отчётами и manifest SHA-256.

Следующие исследования: caller/profile/UseFB условия активации этой ветки;
отсутствующий BR2 и преобразование других FBMemory полей; применение column5
FB-объявлений и состав начальных данных. Согласование всех source settings,
финализация и восстановление остаются условиями будущей аппаратной стадии.
