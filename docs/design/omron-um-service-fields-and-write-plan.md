# Служебные поля UM и локальный план PROGRAM AREA WRITE

Продолжение: [нативная арифметика и финализация](omron-um-native-sums-and-finalization.md).
Позже проверена64-byte зависимость word4 на всех4UM и80-case чистый native
accumulator. Локальная копия независимой4604-byte CXP-сборки с наблюдаемыми
полями целиком совпала с историческим readback. Однако resident256-byte native
quantum ещё не сопоставлен реальному64-byte полю; правило записи не квалифицировано.

16 ноября 2026 года. Исследование выполнено по сохранённым UM, установленным
vendor binaries и локальному W342. В этой сессии запросов к ПЛК не было.
Доступ к действующей установке остаётся **только чтение**; `.36` offline.

## Наблюдаемая зависимость слов0/1

Для каждого аппаратного образа интерпретируем данные как big-endian32-bit
слова. Индексы от нуля. Вычисляем:

```text
S = sum(words[6:]) modulo 2^32
word[0] == S & 0xffff
word[1] == S >> 16
```

| Снимок | Размер bytes | S | Word0 | Word1 | Word4 |
| --- | --- | --- | --- | --- | --- |
| Первый CJ1M | 12380 | 71a29411 | 9411 | 71a2 | c2 |
| Первый CJ1H | 2880 | b89db544 | b544 | b89d | 2d |
| CJ1H после ручной загрузки CXP | 4604 | a2be29a8 | 29a8 | a2be | 48 |
| CJ1H со счётчиками после занятия | 2716 | 44773f74 | 3f74 | 4477 | 2b |

Все четыре пары совпали точно. Независимые Python и Go реализации дали
одинаковый результат. Контролируемое изменение одного байта тела в копии
каждого образа разрушило совпадение. Простой byte sum и XOR не объясняли
пару; младшая половина суммы32-bit слов подсказала нужное разбиение.
Word4 **не совпадает** с переносом полной64-bit суммы — эта гипотеза отвергнута.

Это установленная зависимость в доступном корпусе, а не доказательство полного
нативного алгоритма подготовки загрузки. Не установлены место вычисления
(CX-One/транспорт/CPU), обязательность входных значений при записи и назначение
word4. Слова2/3/5 в четырёх снимках нулевые, но их правила также не обобщаются.

Добавлен диагностический `N1Image.ServiceFields()`: raw первые6 слов,
вычисленный S и `storedPairMatches`. Значения words0/1 сравниваются целиком,
без игнорирования неожиданных старших битов. Файл не изменяется. Несовпадение
не делает обычный compiler N1 структурно повреждённым: библиотечные файлы
обычно содержат здесь нули. `nativeAlgorithmConfirmed` и `writeQualified` false.

## Документированный формат блоков0307

Локальный W342, раздел5-3-11, печатные страницы186–187:

- Только PROGRAM mode; команда не переключает режим сама.
- Program number FFFF,32-bit byte offset, кратный4.
- Data count кратен4, **максимум996 bytes**; у0306 чтения предел992.
- В count последнего блока bit15 установлен. В остальных блоках он снят.
- Payload после command code: FFFF(2bytes), offset(4), count(2), затем данные.

Из этого не следует, что для полной загрузки достаточно просто отправить N1
этими блоками. Штатный порядок подготовки/прав доступа, преобразования образа,
подтверждений/восстановления ещё не квалифицирован.

## Независимый offline план

Добавлены чистый пакет `omron/transfer` и CLI:

```sh
naut omron plan-program-write -block-bytes 996 program.bin
```

Команда только читает локальный файл и печатает JSON. У неё нет endpoint,
`-execute`, сетевого клиента или метода отправки. `-endpoint`/`-execute`
отклоняются до обработки образа. Это кандидатная разметка блока, не загрузчик.

Plan содержит SHA-256 целого образа, точные byte offsets, count/final,
SHA-256 каждого data блока, полный payloadHex и диагностические service fields.
Данные сохраняются целиком, включая неизвестные слова и compiler placeholders.
Нет нормализации, вычисления/вставки новой служебной части, очистки UM,
смены режима, захвата прав или скрытой отправки. Blocks ограничены65536.

Для текущего сохранённого2716-byte UM получено996+996+724 bytes, offsets
0/996/1992; final count82d4. Его исходный SHA-256 остаётся
`d54d9fcb0e4c5f6fb95bc16c31b07fd55a880982835d31b6676af744a1c34a46`.
`networkAccess`, `imageModified`, `wireImageMappingQualified`, `writeQualified`
false. План не привязан к адресу устройства и не разрешает запись на установку.

## Проверки, границы и следующий шаг

Тесты восстанавливают весь исходный файл из payload каждого плана:4/8/992/996
byte блоки, перенос offsets, только один final marker, новые/неизвестные поля,
хеши, независимость от изменений caller bytes. Покрыты malformed N1,
невыравненные/чрезмерные размеры и ограничение числа блоков. Native END-only
файл2624 bytes разбивается996+996+632, что отличает write limit от read limit.
Service test использует независимую сумму native fixture, body mutation и
проверку неожиданных старших битов. Scoped Omron/research и CLI tests, vet прошли.

Следующее: найти нативный путь N1→запись и место подготовки служебных полей,
разобрать word4, квалифицировать ответы/обрыв/чтение обратно на имитаторе,
затем добавить привязанный к конкретному CPU и маршруту проверяемый workflow.
Настройки, инициализация данных, ёмкости и стендовая запись остаются открытыми.
