## Независимая проверка сохранённой пары

Добавлены `commission.ReviewProgramBackup` и команда:

```sh
naut omron audit-program-backup -model "CJ1H-H CPU65" -before status-before.json -after status-after.json first.um second.um
```

Снимки используют обычный status JSON с cpu/status и raw в base64. Декодирование
выполняется заново; сводки сверяются с raw. Проверяются точная модель, полные
identity/status DATA, отсутствие fatal/nonfatal, разбираемость N1, каждый байт
двух UM и арифметическая граница reported capacity. Служебные слова0/1/4 не
маскируются. Неизвестная ёмкость, несовпадение CPU или режима тоже блокируют
согласованность. RUN/MONITOR/PROGRAM допустимы для самого анализа backup;
разрешение записи в PROGRAM из этого не следует.

`readPairConsistent=true` и exit0 означают только прохождение этих проверок.
Конфликт даёт валидный JSON и ненулевой код; некорректный JSON/усечённый ответ
CPU не даёт отчёта. Предел каждого UM16MiB, каждого snapshot1MiB. Пути читаются
только из аргументов; endpoint/execute не поддержаны. Один путь можно передать
дважды, но `independentReadsVerified` останется false.

Во всех сценариях false: observationFreshnessVerified, fullControllerBackup,
restoreQualified, hardwareQualified, readyForWrite, writeQualified, networkAccess.
Это офлайн-проверка предоставленных файлов. Отдельное выполненное сетевое чтение
не превращает её JSON в удостоверенную привязку к endpoint, времени или SID.
Отчёт не принимается как разрешение последующего действия.

Свежая реальная пара прошла проверку. Отдельно прошли9 CLI-сценариев: свежая
пара, те же входные пути, смена режима, изменение identity, ложная сводка,
изменение служебного слова, одинаковый мусор, неверная модель, плохой JSON.
Негативные случаи отвергнуты ожидаемым образом. Go-тесты также проверяют
владение raw-буферами, малую capacity и неполный CPU DATA.

## Кандидат и план возврата

Минимальный LD W0.00/OUT W0.01/END снова собран независимо для CJ1H-H CPU65,
явный BCD/recipe, без FB. Полные2632 bytes совпадают с прежним native-эталоном,
SHA-256 `798dca90199c45dee2c55711d6d9685fba826ae7cb1c66fa98e2bbcb6a76b0f8`.
Локально подготовлены0307-планы и для кандидата, и для сохранённых2716 bytes
исходной программы. Ни один блок не отправлялся. План возврата UM — не выполненное
и не квалифицированное восстановление контроллера.

Preflight по свежим файлам подтвердил модель, границу размера, пару backup
и точную пересборку кандидата; режим RUN отмечен blocked для записи. Остальные
unverified остаются: unit/profile, полная source-settings согласованность,
target layout/finalization, recovery и аудит данных. write-authorization в
офлайн-отчёте тоже unverified: этот формат не удостоверяет сообщение оператора;
подтверждение отключённых механизмов уже сохранено отдельно и не потеряно.

## Выясненный источник version word

Ghidra закрепила три функции CX-P.exe:12684c50,1268c100,1268c110.
Writer12684c50 создаёт `ProgChk` и вызывает CDialog::DoModal (MFC42 ordinal2514).
Только после результата1 и дополнительных проверок применяется выбранное
слово к object+3f8. В отдельной ветке вызывается SetCurrentVersion, когда одно
из двух других WORD-полей равноffff. Семантика этих двух полей здесь не назначена.

Reset1268c100 записываетffff. Presenter1268c110 при таком значении берёт
GetDefaultVersion; иначе форматирует cached word через `%d.%d`.
Это подтверждённая ветка выбора версии в program-check dialog, а не доказательство
чтения unit version физического CPU. Другие writers и сохранение этих полей
в source/ответах устройства остаются неполностью прослеженными. Диалог не запускался.

Корпус `omron/compiler/testdata/program-check-version-origin.json.gz`:32 полностью
декомпилированные функции с прежними этапами и1 прежний частичный asm-фрагмент.
SHA-256 `8eb36346797a113636a504a262c52369f89de35f9408983ccba01b7d6196f4e9`.
`verify_cj1_program_check_version.py` закрепляет14 новых checkpoints, ProgChk,
DoModal, default getter и current setter через IAT/ordinal XML.3422 static checks
прошли на закреплённых бинарниках без исполнения vendor-кода.

Все10 пакетов Omron, Omron CLI и go vet прошли.12 Python replay тестов прошли.
Все9 отдельных CLI backup-review сценариев дали ожидаемые результаты. Новая
команда не выполняла сетевых операций; живое чтение .37 было отдельным этапом.

## Дальнейший порядок

Следующая реализация — состав backup и процедура возврата для ограниченного
program-only опыта, затем привязанный к конкретной сессии FINS sender с точными
ACK, тайм-аутами и остановкой при неопределённом результате. Квалификация полной
палитры инструкций не нужна для минимального опыта, но scope backup/restore,
версия/профиль и границы допустимого обмена должны быть определены явно.

Первую пробу финализации разумно ограничить PROGRAM, передачей минимального N1,
обратным чтением, возвратом исходного UM и его проверкой; исполнение кандидата
проверять отдельно. Это план будущего эксперимента, не реализованная команда.
При отличии readback или ошибке текущий аудит останавливается без auto-retry,
resume или автоматического отката. Исследовательские гипотезы финализации
должны быть помечены как предмет опыта, а не заранее объявлены подтверждёнными.
