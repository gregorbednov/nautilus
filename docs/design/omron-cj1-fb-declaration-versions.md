# CJ1M CPU21 и CJ1H-H CPU65. Версия и типы переменных FB

В заголовке функционального блока CX-One проверяет сочетание языка блока,
направления переменной и её типа. Для CJ1M CPU21 и CJ1H-H CPU65 руководство
Omron указывает минимальную Unit Version 4.0 для переменных In Out и строк
в функциональных блоках. [Omron W394, таблица CJ1-H/CJ1M](https://www.omron-ap.com/data_pdf/mnu/w394-e1-16_cs_cj_nsj.pdf?id=1338).

## Что вернул CX-One

Оба профиля выбраны вызовом `KBaseComp2.Initialise`. Каждый новый локальный
документ `POUHeadDoc.Doc2` получил выбранный профиль через `SetKBase`.
Для 12 сочетаний на каждой модели вызван `ValidateType2` с выбором Ladder
и ST. Типы BOOL, UINT и STRING проверялись как внутренние, входные, выходные
и входы-выходы. Для STRING задана длина 16. Результаты двух независимых
запусков совпали.

| Объявление | Ladder | ST | Требование версии для допустимого объявления |
| --- | --- | --- | --- |
| BOOL или UINT, Internal / Input / Output | Принято | Принято | В этой проверке признака 4.0 нет |
| BOOL или UINT, In Out | Принято | Принято | 4.0 |
| STRING, Internal или In Out | Ошибка типа | Принято | 4.0 |
| STRING, Input или Output | Ошибка типа | Ошибка типа | Требуется изменить объявление |

Из 48 проверок языка и типа 36 завершились успешно и 12 дали ошибку.
Дополнительно в каждом из 24 документов объявление было записано штатным
`AddVariable2` и считано через `GetItem2` с проверкой имени, направления,
типа и длины. Метод `IsUsedTypeStringOrVerInOut` дал 1 для In Out любого
из трёх проверенных типов и для внутренней STRING. Для входной и выходной
STRING он дал 0, хотя проверка типа отклонила такие объявления. После
удаления тестовой переменной признак вернулся к 0.

## Как это использует Nautilus

`naut omron inspect FILE.cxp` и `FILE.cxt` возвращают найденные ограничения
в `fbDeclarationFindings`. У каждой записи есть путь к таблице объявлений
и строка, имя переменной, направление и тип. Для допустимого сочетания
с ограничением версии выводится `minimumCJ1UnitVersion`, для ошибочного —
`issue`. Область разбора — строки распознаваемого формата `PouVarList` в
заголовках `FBLadder` и `FBST`. В лестничных проектах сборка теперь
указывает конкретное объявление с неподдерживаемым In Out или недопустимой
STRING.

В переносимом тесте объявления подставлены в копии пользовательских заголовков.
Вариант ST в этом тесте синтетический. Результаты проверки типов ST получены
непосредственно от `ValidateType2`.

В четырёх пользовательских CXP под `projects` проверено по семь объявлений.
Этих ограничений в них не обнаружено. Каждый проект с прежними явными
настройками дал побайтно прежний N1 (4604 байта). В двух изменённых копиях
диагностика сборки указала на введённую ошибку в строке 551.

## Воспроизведение и следующая проверка

Из корня Nautilus выполнить `go test ./omron/cxp -run TestFBDeclarationNativeConstraints -count=1`.
Тест использует сохранённую матрицу `omron/cxp/testdata/native-fb-header-versions.json`.
Для повторной нативной записи запустить `tools/omron-research/Measure-CJ1FBHeaderVersion.ps1`
в Windows PowerShell x86. Первичные результаты, повтор и отчёты по проектам
лежат в `C:/cx-proger/research/cj1-fb-header-versions-20261120-01`.

Версия 4.0 взята из спецификации Omron. В этом опыте версия полной проверки
программы не переключалась. Следующий эталон — два проекта с вызовом FB:
Ladder с In Out BOOL и ST с внутренней STRING. Для каждого нужны результат
полной компиляции под Program Check Version 3.0 и 4.0, диагностика и N1
для принятого варианта. Они позволят проверить размещение параметров и код вызова.

### ST с внутренней строкой и вызовом из задачи

На CJ1M CPU21 и CJ1H-H CPU65 проверены два этапа офлайн-сборки. На первом
штатный StructuredTextCompiler получил заголовок FB с внутренней переменной
`Msg` типа STRING длиной 16 и текст:

```iecst
Msg := 'ABC';
Result := Gate;
```

Для обеих моделей Build вернул 1 с нулём ошибок и предупреждений. Компилятор
выдал `1#MOVL #43004142 3,BR3`, `1LD 2,BR3`, `1OUT 3,BR3`. Адрес
`3,BR3` для Msg имеет единицу «слово», для Result — «бит». Заголовок
сообщил 181 бит в BR3, что занимает 12 слов. При замене тела на
`Msg := ;` Build вернул 0, пустой список инструкций и одну ошибку
`Invalid expression` в первой строке.

На втором этапе CX-Pdata получил эти инструкции, размеры банков и
проверенную ранее задачу с вызовом одного экземпляра BLINK. Для каждой
модели выполнены отдельные сборки с Program Check Version и Local Current
Version 3.0 и 4.0. Для задачи, определения и экземпляра журнал содержит
выбранную версию и успешный возврат. Все четыре N1 побайтно совпали
(3128 байт, SHA-256 `95abccf8c1a2d4002e5240173ff641d91efadc3380875f3e3f7736d458bf1f55`).
Проверка Go воспроизводит этот образ из скалярного CXT, измеренного
перемещения литерала, инструкции присваивания BOOL и размера BR3.

Заголовок с объявлением STRING передавался только на первый этап.
Совпадение образов при двух версиях оставляет открытым результат F7 для
целого проекта. Для следующего опыта нужен сохранённый проект с вызываемым
ST-блоком и результат F7 для каждой версии. Аналогичная проверка требуется
для Ladder с In Out BOOL. Из 681 файла CXF установленной библиотеки
`CX-One/Lib/FBL` все распакованы существующим декодером Nautilus, строка
`FBST` не встретилась ни разу. В этом опыте обмен с ПЛК отсутствовал.

Из корня Nautilus переносимая проверка выполняется двумя командами:

```sh
go test ./omron/compiler -run TestSTStringWriterReference -count=1
python -B tools/omron-research/verify_cj1_st_string_body.py
```

Исходные журналы и оба повторных захвата находятся в
`C:/cx-proger/research/cj1-fb-source-compilation-20261120-01`. Если передать
этот каталог проверяющему скрипту, он дополнительно проверит хеши файлов
захвата и сравнит журналы и четыре N1 с сохранённым эталоном.
Для нового измерения запустить `Measure-CJ1STStringBody.ps1` в 32-битном
Windows PowerShell и сохранить его JSON в UTF-8. В
`Invoke-CJ1InstructionOracle.ps1` передать этот файл через `-STStringBody`
с единственным case `invocation-link`, ключами `-ProgramObjectProbe
-InstanceBindingProbe -BindingInputLifecycle source -TimerCounterMode bcd`
и явно заданной одинаковой версией в `-LocalCurrentVersion` и
`-ProgramCheckVersion`. Для каждого запуска нужен отдельный выходной каталог.

### F7 для целого проекта на CJ1H-H CPU65

20 ноября 2026 г. оператор выполнил F7 в CX-Programmer для NewPLC1.
В исправленном проекте `CJ1H-ST-Gate-fixed.cxp` задача NewProgram1
вызывает экземпляр Probe1 в первой ступени секции HM. Контакт EN использует
W100.00, графические параметры FB_INPUT и FB_OUTPUT связывают Gate с W100.01
и Result с W100.02. ENO свободен. ST_Probe содержит объявление внутренней
STRING длиной 16 и приведённый выше исходный текст.

В журнале Compile присутствуют HM и ST_Probe. Итог при Unit Ver.4.0 —
0 ошибок, 79 предупреждений. Из них 78 относятся к повторным записям
выходов в POWER, UP, DOWN и Doors, одно — к неиспользуемому BLINK_L2.
В предыдущем прогоне с отдельным контактом вместо параметра Gate была
ошибка отсутствующего входа в HM. Исправленная ступень прошла F7.

В каталоге стенда `C:/cx-proger/research/cj1-f7-projects` сохранены CXP
(SHA-256 `4571a4ffa821ea3f36784aca90e739a741cd7ad0b31f60df1f553b3595fdc51d`)
и исходный журнал `CJ1H-ST-Gate-fixed-F7-v4.txt`
(SHA-256 `7a39ee7cd1824aaaaaf79e0c908a6437a716dff85d392436b4d54730b44eb4da`).
Для этой версии целого проекта осталось получить N1 для побайтной сверки.

Оператор переключил только Program Check Options на Unit Ver.3.0 и повторил
F7. В журнале указан CJ1H-H CPU65 и подтверждена версия проверки 3.0.
Итог — одна ошибка совместимости STRING или Input Output и одно предупреждение
о BLINK_L2. В двух таблицах PouVarList этого проекта нет переменных In Out.
Единственное строковое объявление — внутренняя Msg в ST_Probe. Таким
образом, F7 отклоняет данный проект с STRING при 3.0 и принимает при 4.0.
Копия текста из сообщения оператора сохранена рядом с журналом 4.0 в
`CJ1H-ST-Gate-fixed-F7-v3.txt`. Для Ladder с переменной In Out и для CJ1M
нужны отдельные проверки целого проекта.

### Пара проектов для проверки Ladder In Out

`make_cj1_ladder_inout_probe.py` принимает сохранённый `gate-fixed.cxt`
и выходной каталог. Оба результата содержат графический вызов Probe1
в секции HM и одно определение LD_Probe вместо ST_Probe. В теле LD_Probe
нормально замкнутый контакт SharedBit управляет катушкой. В контрольном
проекте катушка записывает отдельный выход Result (W100.02). В опытном
проекте v2 катушка записывает тот же SharedBit, объявленный In Out. Обе
стороны параметра в графическом вызове связаны с W100.01, EN — с W100.00.
Такое представление обеих сторон проверяется экспериментально через F7.
Передачу адреса для In Out описывает [Omron W447, раздел 2-1](https://assets.omron.eu/downloads/manual/en/v2/w447_cx-programmer_fb_st_operation_manual_en.pdf).

Для CPU65 библиотека PHeadDoc с нулевым онлайн-резервом вернула размеры
банков в битах 0/0/0/4/0 для контроля и 0/0/0/34/0 для In Out.
Метод IsUsedTypeStringOrVerInOut вернул соответственно 0 и 1.
Исходники эксперимента и файлы CXP сохранены в
`C:/cx-proger/research/cj1-f7-projects`.

В первом проекте генератор записал в PouVarList код 3 из COM API.
При F7 на 4.0 и 3.0 CX-Programmer сообщил три одинаковые ошибки:
два параметра без соответствующих выводов блока в HM и невозможность
связать внешнюю переменную SharedBit. В обоих случаях было также одно
предупреждение о неиспользуемой переменной. Эти прогоны устанавливают
значение кода 3 (External) в файле проекта.

В поставляемых Omron файлах `_G3ZA203_ReadVariableN10.cxf` и
`_G3ZA406_WriteVariableN10.cxf` строки ReadData и WriteData начинаются
с кода 4. В описании `_G3ZA203_ReadVariableN.pdf` ReadData указана
в группе Input/Output Variables. Эти файлы установлены в
`CX-One/Lib/FBL/omronlib/PowerController/G3ZA/Serial`.
Nautilus теперь различает коды файла 3 (External) и 4 (In Out).
При сборке внешнее объявление требует отдельной реализации связывания.

После распаковки `CJ1H-Ladder-InOut-v2.cxp` отличается от предыдущего
исходника одним байтом в строке 303: кодом направления SharedBit.
SHA-256 исправленного CXP — `788736c33281e3e5af92998c91d7cef6d14686c467d9cd2f9a3655d5ec80f2e2`.
При F7 на v2 обе версии (4.0 и 3.0) дали одну ошибку и одно предупреждение.
В HM осталась ошибка расположения правого параметра в (4, 2); диагностика
по левой ячейке (1, 2) и ошибка связывания External исчезли. Для LD_Probe
обе проверки всё ещё сообщили `Unreferenced variable 'SharedBit'`.
По этим прогонам установить результат версионной проверки In Out нельзя.

В разделе 1-2 W447 указано, что для In Out адрес задаётся со стороны входа,
а выходной адрес редактор подставляет автоматически. В следующем опыте
`CJ1H-Ladder-InOut-v3.cxp` убрана отдельная графическая ячейка FB_OUTPUT
в (4, 2). В графике HM осталось четыре элемента: контакт EN, вызов Probe1,
левый FB_INPUT с W100.01 и провод EN. В распакованных CXT v2 и v3 отличаются
только строки списка элементов этой ступени. Объявление и тело LD_Probe
совпадают. SHA-256 CXP v3 — `ceac14b9a79d8f427db52058d7d94a3e7e5ce5471f75d045e39b6f98e6b83123`.
Для этой копии оператор выполнил F7 на CJ1H-H CPU65 с обеими версиями проверки.

| Unit Ver. | Ошибки | Предупреждения | Диагностика |
| --- | ---: | ---: | --- |
| 4.0 | 0 | 80 | 78 повторных записей выходов, неиспользуемый BLINK_L2 и `Unreferenced variable 'SharedBit'` |
| 3.0 | 1 | 2 | Ошибка совместимости STRING или Input Output; предупреждения о BLINK_L2 и SharedBit |

В HM ошибка положения параметра исчезла при обеих версиях. В v3 нет
объявлений STRING; проверка 3.0 отклоняет проект с In Out BOOL. В графике
LD_Probe имя SharedBit присутствует у контакта и катушки, однако предупреждение
о неиспользуемой переменной сохраняется. Для подтверждения исполняемой
семантики нужно получить N1 успешной сборки 4.0 и проверить по коду,
как вызов передаёт W100.01 и как тело обращается к переданному адресу.

### Сохранённые N1 и пустое тело LD_Probe

В каталоге TEMP стенда после опытов сохранились два файла. Nautilus разобрал
оба как полные N1 с задачами MotorDrive_LIFT_1 и NewProgram1. Имя второго
определения, имена задач, адреса параметров и время записи согласуются с
соответствующими проектами. Временные файлы скопированы после F7, поэтому
прямой трассы, связывающей writer с хешем исходного CXP, для них нет.

| Временный файл | Определение | Размер N1 | Слова между FBBN и FBBRET |
| --- | --- | ---: | ---: |
| BINBDB1.tmp | LD_Probe | 4952 байта | 0 |
| BIN87D9.tmp | ST_Probe | 5000 байт | 6 |

У LD_Probe весь код определения состоит из четырёх слов: вход с номером
1025 и возврат. В задаче перед FBICALL 8/1025 находится последовательность
`927f0144 520de641 5d17f00a`; у ST_Probe с обычным BOOL-входом на том же
W100.01 — `927f0147 620de641 5717e009`. В обоих экземплярах найден вызов
тела 1025. В ST_Probe записан перенос литерала ABC и присваивание BOOL.
В LD_Probe v3 отсутствуют инструкции чтения и записи SharedBit внутри тела.
Проверка двух эталонов из testdata: `python -B tools/omron-research/verify_cj1_f7_probes.py`.

Генератор v3 копировал семь графических ячеек из BLINK с FBDefVer 1.9
в LD_Probe с FBDefVer 2.0. В штатном Ladder-экспорте Omron
`_G3ZA203_ReadVariableN10.cxf` (2.0) у контакта, катушки и провода
присутствует дополнительное нулевое поле после четвёртого столбца.
В CJ1H-Ladder-InOut-v4.cxp добавлено только это поле у семи ячеек LD_Probe.
При F7 для v4 с Unit Ver.4.0 оператор получил 0 ошибок и 79 предупреждений.
Предупреждение о SharedBit исчезло. Остались 78 сообщений о повторной
записи выхода и одно о неиспользуемом экземпляре BLINK_L2.

После этого прогона в TEMP найден BINEF03.tmp (5004 байта, SHA-256
`8a5cba1a0b147ec3dce7507311b75b9de4833857239d3596f5e15679156683d7`).
В определении LD_Probe между входом 1025 и возвратом появились 13 слов.
Вся разница с N1 для v3 — вставка этих 52 байт и четыре скорректированных
поля длины и смещения. Секции экземпляров и задач совпадают побайтно.
Переносимый тест сохраняет точные слова тела и проверяет тот же вызов
8/1025. Этот опыт подтверждает генерацию непустого тела по двум графическим
операндам; выполнение на ПЛК и независимое кодирование этих форм остаются
отдельными проверками.

### Сборка тела LD_Probe в Nautilus

Для CJ1H-H CPU65 с явно указанными Unit Version 4.0 и режимом BCD
команда ниже читает ячейки FBDefVer 2.0 из проекта v4. Поддержана одна
ступень: нормально замкнутый контакт и катушка одной переменной In Out
BOOL. Два неявных бита и двухсловный адрес занимают 34 бита, или три
слова BR3 с округлением. Кодирование использует измеренную форму инструкций
именно для этого сочетания операндов и логического контекста.

```sh
naut omron compile-fb-definition-body -model "CJ1H-H CPU65" -unit-version 4.0 -timer-mode bcd -definition "Resource[0].FunctionBlocks.FunctionBlockWrapper[1].FunctionBlock" CJ1H-Ladder-InOut-v4.cxp
```

Тест `TestInOutBOOLBodyFromLadder20` сравнивает все 52 байта с телом
определения из сохранённого N1. Переименование переменной сохраняет код.
Замена полярности контакта или адресата катушки, подмена направления,
старая форма ячейки, профиль CJ1M и версия 3.0 не проходят этот путь.
Следующий этап — генерация экземпляра и вызывающей задачи с передачей
адреса, затем побайтная сверка связанного N1.
