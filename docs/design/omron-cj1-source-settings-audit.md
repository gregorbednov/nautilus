# CJ1: сверка сохранённых настроек памяти CXP

Дополнение: [BR2 и FB-профиль](omron-cj1-br2-and-fb-profile.md) подтвердили
пропуск BR2 при чтении/записи/применении и таблицу DIFF8191,0. Аудит отдельно
сверяет эту таблицу с рецептом; присутствие BR[2] не делает source-настройку
применяемой. Активный профиль и начальные данные остаются unverified.

Уточнение: [UseDefault и путь к KBase](omron-cj1-stack-source-origin.md) объяснили
неактивность сохранённого D0 при отсутствующем UseDefault. Предыдущая безусловная
классификация D0/AC0 как blocked исправлена: для этих проектов stack-address
теперь unverified, а совпадение pinned default-table проверяется отдельно.
Ниже сохранены исходные наблюдения полей; их эффективное применение условно.

18 ноября 2026 года. Продолжение [проверки рецепта](omron-cj1-build-reproduction.md).
Добавлены `compiler.AuditCXPImageSettings` и локальная команда:

```sh
naut omron audit-image-settings -model "CJ1M CPU21" -resource "Resource[0]" -settings omron/compiler/testdata/n1-example-settings.json project.cxp
```

Команда читает CXP/CXT и явный JSON рецепта, ничего не записывает и не подключается
к устройствам. Settings проходят прежнюю строгую проверку. Аудит сравнивает
только перечисленные ниже текстовые поля памяти; он не утверждает полную
эквивалентность рецепта настройкам проекта или CPU. Модель здесь — вход рецепта,
а не подтверждение модели из PLC.Config или opaque PLC.Settings.Data.

## Факты из четырёх пользовательских проектов

Проверены все четыре `.cxp` из `projects`: два исходных проекта 2023 года и две
версии `elevator-new4`. Оригиналы сохранены побайтно; распакованные CXT остаются
в исходной кодировке. Все четыре проекта имеют одинаковые исследуемые поля:

| Сохранённое поле | Значение | Сверка с явным рецептом |
| --- | --- | --- |
| FBMemory.BR[0] | T3072,1024 | passed: точное текстовое совпадение |
| FBMemory.BR[1] | C3072,1024 | passed: точное текстовое совпадение |
| FBMemory.BR[2] | Поле отсутствует | unverified: DIFF8191,0 не выводится автоматически |
| FBMemory.BR[3] | H512,896 | passed: точное текстовое совпадение |
| FBMemory.BR[4] | H1408,128 | passed: точное текстовое совпадение |
| NumRegisters | 5 | passed: совпало число регистров, не наличие каждого поля |
| StackSettings.StartAddress | D0 | Неактивен при UseDefault; рецепт задаёт AC0 |
| StackSettings.WordSize | 1472 | Сохранено без подтверждённого преобразования |
| StackSettings.BitSize | 64 | Сохранено без подтверждённого преобразования |
| ShareSFCMemoryWithFBNonRetain | true | Семантика совместного использования не квалифицирована |

В частности, NumRegisters=5 не делает отсутствующий BR[2] равным нулю или
DIFF8191. D0 не заменяется на AC0. Даже числовое совпадение 1472+64=1536 не
доказывает единицы/смысл WordSize и BitSize относительно FirstSize/TotalSize.
Формула явной ветки и default-selection теперь прослежены отдельно; runtime/profile-условия ещё не квалифицированы.

В каждом проекте одна исследуемая таблица FB из семи объявлений. Пять строк
содержат непустой столбец с индексом 5 (нумерация с нуля): ON=FALSE, PV=0,
PN=0, IN=FALSE, OUT=FALSE. Строки TIMER_1/TIMER_2 имеют пустое значение.
Отчёт сохраняет имена, пути, номера строк и точное написание значений.
Формат остаётся `column5`: назначение и исполняемая семантика этих данных
не объявляются квалифицированными. Существующий компилятор сохраняет размещение,
но не формирует отдельные начальные данные. FALSE/0 не считаются автоматически
избыточными: состояние реальной/retained памяти этим источником не определяется.

## Контракт отчёта

`format=cj1-source-settings-audit`; хеш относится к исходным CXP/CXT bytes,
а `sourceEncoding` показывает декодированную кодировку. `savedMemory` сохраняет
скалярные поля FBMemory в исходном порядке, включая raw spelling и строки.
Проверки различают `passed`, `blocked`, `unverified`; passed означает только
текстовое совпадение отдельного поля. Нет суммарного признака пригодности
для загрузки. Порядок инвентаризации объявлений детерминирован.

Дубликаты путей в выбранном resource, неверный/отсутствующий resource и
неподдержанная форма таблицы отвергаются без отчёта. Отсутствие FBMemory
не заполняется неявными defaults. JSON/N1-рецепт не получает новых значений.

Всегда сохраняются `sourceSettingsVerified=false`, `storageInitialized=false`,
`globalStorageAudited=false`, `hardwareQualified=false`, `writeQualified=false`,
`networkAccess=false`. CLI публикует валидный отчёт и возвращает ненулевой код:
сверка неполна, даже когда синтетически исправлены все сравниваемые поля.
Оригинальные проекты, N1 и настройки не редактируются.

Не проверены opaque PLC.Settings.Data, timer/option flags, SFC, global/local
symbols, операнды и реальные эффекты памяти. Этот аудит не снимает соответствующие
ограничения preflight и не является генератором инициализации или full backup.

## Проверка и следующий шаг

Прошли тесты всех 10 пакетов Omron, Omron CLI и `go vet`. Отдельные 7 вызовов
CLI проверили четыре настоящих CXP и три синтетических варианта: совпавший AC0,
явный BR[2] и дублированное поле. Это результаты первоначального этапа.
Текущий аудит, уточнённый реверсом reader/writer/bridge, сохраняет BR[2]
неприменяемым даже при совпадении текста; отдельно сравнивает default-table.
Дубликат по-прежнему отвергается без отчёта.
Материалы: `research/hardware/20261118-cj1-source-settings-01`, включая исходники,
CXT, команды, stdout/stderr, тестовые журналы и manifest SHA-256.
Обращений к ПЛК и запуска vendor runtime в этом этапе не было.

Далее: проследить CXP FBMemory/StackSettings → фактические поля KBase/compiler;
отдельно установить применение столбца5 FB-объявлений и состав сегмента начальных
данных. Затем расширить аудит на абсолютные адреса, сохранённые экземпляры,
глобальные/локальные символы и пересечения памяти. Финализация, полный backup и
восстановление остаются самостоятельными условиями аппаратной стадии.
