# CJ1: журналируемое управление и первый опыт PROGRAM/RUN

19 ноября 2026 года. Продолжение [wire API режима/доступа](omron-cj1-mode-access.md).
Добавлен `commission.NewControlledProgramSession`: явные control шаги работают
на выделенном соединении и используют тот же синхронный журнал, что0307.
На настоящем CJ1H/.37 выполнен mode-only опыт без загрузки программы. Первая попытка CJ1M
была отклонена auto-review; после явного разрешения оператора аналогичный опыт
[успешно завершён](omron-cj1m-mode-only-2026-11-19.md). Изоляция обоих
контроллеров ранее подтверждена оператором; она не измерялась инструментами.

## Порядок действий

1. `Prepare` читает стабильные rawCPU/status и два совпадающих N1 в текущем
   PROGRAM/MONITOR/RUN, затем сохраняет backup/candidate/observations/manifest.
   До успешного сохранения control команды не отправляются.
2. `EnterProgram` сверяет текущий UM с приватным backup, проверяет target/errors,
   журналирует и отправляет обычный0C01, затем STOP0402 и подтверждает PROGRAM
   чтением identity/status. Каждая попытка сохраняется до команды, ACK — после.
3. `WriteCandidate` требует завершённого control шага и заново проверяет CPU,
   PROGRAM и исходник. Все прежние проверки0307/ACK/readback сохранены.
   Успех оставляет соединение открытым для явного дальнейшего действия.
4. `RequestExecution(RUN|MONITOR)` — отдельное действие, не автоматический
   возврат исходного режима. Перед0401 заново читается и сохраняется весь UM,
   он должен совпасть с кандидатом, возвращённым исходником либо неизменённым
   backup в mode-only опыте без0307. После ACK требуемый режим подтверждается
   чтением. Второй запрос исполнения и последующая запись в этой фазе запрещены.
5. `FinishProgram` проверяет target/ожидаемый режим, явно отправляет глобальный
   RELEASE0C03, сохраняет ACK и последующее наблюдение, закрывает соединение.
   CPU остаётся в последнем явно заданном режиме. Finish разрешён и после
   EnterProgram без передачи кандидата; автоматического RUN при этом нет.
6. `ReturnOriginal(freshClient)` требует явного завершения предыдущего
   подтверждённого доступа. В новой сессии заново выполняются0C01/0402/status;
   прежний access ACK не наследуется. Передаётся только приватный исходник.
   После readback тоже нужны отдельные RequestExecution/Finish, если они требуются.

`NewProgramSession` сохранён для совместимости как прежний экспериментальный
API с внешним PROGRAM/access; новые методы доступны только controlled варианту.
Ни один конструктор не квалифицирует аппаратную загрузку или полный backup.

## Ошибки и границы подтверждения

При любой ошибке control/readback/journal/guard — stopped и закрытие соединения.
Нет retry, reconnect, forced0C02, автоматического RUN/RELEASE/возврата программы.
Если право могло быть получено, snapshot показывает accessState=uncertain:
закрытие TCP не доказывает освобождение. После полного сохранённого ACK0C03
state=released означает наблюдавшийся ACK, не постоянную гарантию свободного права.
RELEASE глобален и может затронуть другой узел; исключение параллельных клиентов
остаётся внешней предпосылкой. При потере связи может потребоваться ручной разбор.

Обычный3001 сохраняет owner и end code в stop событии и в обёрнутой Go ошибке;
errors.As продолжает работать. Журнал сохраняет binding каждой control попытки,
requested mode и фактический raw status, в том числе при несовпадении режима.
Передаваемые журналу указатели requestedMode — отдельные копии: модификация
события не может превратить STOP в RUN или изменить приватный expected mode.
Исторический успешный UM readback в audit не является текущей гарантией после
последующих ошибок: смотреть state/stopReason и весь журнал.

Файловый журнал сохраняет прежние свойства: эксклюзивный новый каталог,
Sync/Close перед успехом, блокировка после ошибки, отсутствие load/resume.
Потеря питания/метаданные каталога на всех filesystem не квалифицированы.

Добавлено9 top-level tests: полный цикл candidate/finish/fresh-original return,
отказы backup/control-intent/control-ACK, потеря ACK acquire/STOP/release/RUN,
3001 с owner, неподтверждённый режим, изменившийся UM, отсутствие автоочистки,

проверен на обоих CPU профилях, включая разные negotiated source nodes.
Mode-only испытание отдельно проверено для RUN и MONITOR без записи программы.

CGO_ENABLED=0, зависимости offline). Production CLI остаётся читающим.

## CJ1M и дальнейшие шаги

Для CJ1M/.36 подготовлен отдельный mode-only драйвер, локальная пересборка
рецепта прошла. Реальный запуск отклонён auto-review до создания процесса:
review сохранил прежнюю offline/no-poll трактовку и потребовал отдельного
разрешения именно на mode/access операции. Пользователю задан соответствующий
вопрос; обход отказа или повтор запуска без ответа не выполнялись. Затем
оператор явно ответил «Разрешаю этот опыт на CJ1M», и согласованный цикл
успешно завершён с новым4672-byte UM, уже находившимся в CPU до control шагов.
Подробности и новый frozen пакет — в [последующем отчёте](omron-cj1m-mode-only-2026-11-19.md).
До этого разрешения последние реальные данные CJ1M были чтением от18 ноября: RUN, UM4652 bytes,
SHA256 d0df6478c25a126575710f3ed9895a6c7f6d2889ccfcb79aa850c6c3b91eee2a.

Mode-only проверка теперь завершена на обоих CPU. Для первого0307
опыта нужны отдельные target protection/service и profile/finalization проверки,
backup вне UM и конкретный сценарий возврата. Обычный mode/access путь CJ1H
уже наблюдён; неизвестное поведение при обрыве и полная аппаратная загрузка
не объявляются проверенными. Прочие задачи полного компилятора сохраняются.
