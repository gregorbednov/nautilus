# Аппаратная проверка CJ1M/CJ1H и передача разработки

## 22 ноября 2026 — CJ1M восстановлен, причина расхождения при загрузке открыта

После передачи Program из CX-Programmer исходный образ снова прочитан с CPU21.
В PROGRAM ещё присутствовали 80F1 и A403=1000. Адресное снятие ошибки вернуло
0000. Две последующие выборки подтвердили нулевые активные ошибки и A403;
историческая запись сохранилась. Перед отдельным запросом RUN повторно прочитаны
4672 байта исходной UM. Три новых соединения после RUN вернули статус 05/04,
нулевые ошибки, A403=0000 и активный TK0.
[Записи восстановления](../../omron/commission/testdata/bench-original-rewrite-20261122/cj1m/recovery).

В неудачном опыте Nautilus отправил четыре блока по 996 байт и последний
блок 688 байт с флагом завершения. Обратное чтение в PROGRAM в обоих опытах
совпало с одной исходной UM. Различие проявилось при исполнении. В архиве нет
обмена **успешной передачи Program из CX-Programmer**: захват br-plc содержит
отказ при смене режима. При восстановлении также отдельно снималась ошибка.
Эти данные не позволяют приписать результат конкретному действию финализации.

Следующий эталон — полный захват штатной передачи Program на выделенном стенде:
от последней проверки статуса до первого подтверждённого исполнения после
передачи. Сопоставить обращения к областям памяти, содержимое и границы блоков,
последний ACK, все промежуточные команды и ответы, смену режима и флаги
исполнения. Привязать захват к модели, проекту и SHA-256 обратного чтения.
Офлайн-проверка обеих имеющихся последовательностей выполняется командой
`python -m unittest discover -s scripts -p test_omron_sample_bench_state.py`
из корня Nautilus.

## 22 ноября 2026 — CJ1M, исходная UM записана, запуск завершился MEMORY ERR

Аппаратная приёмка записи для эксплуатации остаётся открытой. До выяснения
причины ошибки остановлены опыты с загрузкой на обоих CPU. В тот момент
независимое чтение CJ1M вернуло режим RUN, остановленное исполнение, fatal
8000 и код 80F1. Оператор уведомлён для диагностики и восстановления CX-One.

1. Две свежие копии исходной UM каждого CPU совпали с архивами; четыре
   области параметров каждого CPU совпали с парными копиями 20 ноября.
   В последовательных выборках RUN на CPU65 совпали все 36 наблюдаемых
   элементов, на CPU21 совпали 60 из 80. Это наблюдение при имевшихся
   физических входах. [Снимки RUN](../../omron/commission/testdata/bench-run-20261122).
2. На CPU21 в PROGRAM отправлены пять блоков исходной UM (4672 байта),
   с подтверждением каждого. После освобождения права управления новое
   соединение прочитало точную копию. У PLC Setup, I/O Table, Routing и CPU Bus
   суммарно 14976 байт совпали до и после. В выборках PROGRAM отличалось
   только CIO2098 (04AC → 04AD), оно также менялось в предыдущих опытах.
3. В отдельном сеансе повторно сверены байты, получен ACK на RUN.
   Следующее чтение 0501 вернуло 0080, штатная последовательность остановилась
   до освобождения права. Новый независимый запрос 0601 вернул 0080 с DATA
   04 04 80 00 00 00 00 00 80 F1 и полем сообщения. Чтение A403 вернуло
   0080 с DATA 10 00. W393 относит 80F1 к ошибкам памяти. Установлен бит
   A403.12; его причина для этого CPU требует отдельного подтверждения.
   [Журналы записи, запуска и сырые ответы](../../omron/commission/testdata/bench-original-rewrite-20261122/cj1m)
   и [Omron W393, §11-2](https://assets.omron.eu/downloads/latest/manual/en/w393_cj1m_g_h_cpu_units_operation_manual_en.pdf).

До дальнейших записей зафиксировать диагноз CX-One и восстановление
штатного исполнения, подтвердить RUN, нулевые ошибки и идентичность UM
независимым чтением. Для выяснения причины сравнить успешную штатную
передачу и завершение загрузки CX-One с журналом 0307. Результат PROGRAM
подтверждает транспорт и обратное чтение; критерий приёмки включает
исполнение исходной программы после записи.

При проверке возврата в RUN отдельно проверить бит 0 первого байта DATA
ответа 0601. Он показывает исполнение пользовательской программы; второй
байт показывает выбранный режим. В аварийном ответе CPU21 оба байта равны
04, в исходных снимках RUN они равны 05 и 04. Проверка запуска и скрипт
приёмки снимков RUN теперь отклоняют режим RUN с выключенным битом
исполнения даже при нулевых масках ошибок. [Omron W342, §5-3-17](https://files.omron.eu/downloads/latest/manual/en/w342_cs_cj_cp_nsj_communications_commands_reference_manual_en.pdf).

При разборе причины учитывать границы документации. В таблице MEMORY ERR
руководства W393 для CJ1 перечислены A403.00, .04, .05, .07, .08, .09
и .10. Значение .12 для CPU21 по этой таблице определить нельзя. Описание
0307 в W342 требует режима PROGRAM, выравнивания и флага последнего
блока. Журнал опыта подтверждает эти условия. Для установления различий
при завершении штатной загрузки нужен обмен успешного восстановления
или подробная диагностика CX-Programmer.

Захват на br-plc 22 ноября дал причину отказа CX-Programmer при ручном
переходе в PROGRAM. В 02:18:47.394343 МСК с 10.0.174.210 на 10.0.174.36
по UDP/9600 ушёл FINS STOP (0402, FFFF, SID 63 hex). В 02:18:47.572261
пришёл ответ с тем же SID и командой, end code 3081. По W342 §5-1-3
это 3001 (нет права управления) с флагом 0080. Ответ STOP не содержит
адреса владельца. В записанном окне CX-Programmer не отправлял программу.
Отказ доступа к STOP и причина MEMORY ERR при исполнении — разные вопросы.
SHA-256 декодированного `cx-br-plc.pcap`:
`a2ef986b0b7ee3f033d3afe105e4b683d6db2d55228db37a9e2d56265b6b56df`.

## Воспроизводимая офлайн-проверка перед стендом, 21 ноября 2026

Для CJ1M CPU21 и CJ1H-H CPU65 запустить из корня репозитория с Go
версии, указанной в `go.mod`, и Python 3. Потребуется доступ к зависимостям Go или
заполненный кэш модулей. Архивы стенда, CX-One и подключение к ПЛК для
этих команд не требуются.

```sh
go test -count=1 ./omron/...
go test -count=1 ./cmd/naut -run '^(TestOmron|TestCompileReadbackSTDefinitions)'
python -B -m unittest discover -s scripts -p test_omron_sample_bench_state.py -v
```

| Что проверяется | Эталон и критерий |
| --- | --- |
| Сборка для каждой модели | `TestOmronCompileImageCLIProducesExactNativeFiles` собирает два проекта и сравнивает результат с соответствующим N1 в Git. |
| Считанный проект CPU21 | `TestCompileReadbackSTDefinitions` сверяет обе ST-записи. `TestRebuildFromCXUpload` проверяет SHA-256 образа, затем вычисляет три служебных слова и сверяет SHA-256 с архивной UM. Используются внешние настройки исследованного образа. |
| Резервная копия и соответствие кандидата CPU | Тесты `omron/commission` и команд preflight, backup-review и compare-readback проверяют согласованность копий, модель, размер и несовпадения. |
| Сбой передачи и возврат | Тесты `omron/transfer` и `omron/commission` моделируют ошибки подтверждений, неполный обмен, журналирование и отдельный сеанс возврата исходной программы для обеих моделей. |
| Целостность снимков состояния | Python-тест воспроизводит обе серии для каждого CPU. В отдельных копиях меняется по одному байту ответа идентификации или статуса. Верификатор сверяет поля JSON с исходными байтами и отклоняет смену идентичности между снимками. |

Затем проверены явные назначения BOOL-кандидатов. Для повторения собрать

по словам; флаги завершения таймеров учитываются отдельно. Отчёт описывает

### Внутреннее состояние BOOL-control и критерии отката

21 ноября оба CPU в RUN дважды вернули A500 = 0000. Идентификация и
статус обрамляют каждую пару чтений. A500.12 (IOM Hold) и A500.13
(Forced Status Hold) были выключены. Для проверки активных форсировок
понадобится отдельный список. Настройки удержания этих битов при включении
питания имеют отдельный смысл. [Парные чтения](../../omron/commission/testdata/bench-bool-hold-20261121)
и [руководство Omron W393, раздел 7-2](https://assets.omron.eu/downloads/latest/manual/en/w393_cj1m_g_h_cpu_units_operation_manual_en.pdf).

| Объект | Что сравнить до опыта и после возврата исходной UM |
| --- | --- |
| Код и настройки | На каждом CPU новым сеансом прочитать UM в PROGRAM и побайтно сверить с исходной UM этого CPU. Повторить парные чтения PLC Setup (1024 байта), I/O Table (2560), Routing (1024), CPU Bus (10368) и сверить с копиями непосредственно перед опытом. Архивы 19 и 20 ноября дают контроль длины и содержимого. Отдельно сверить идентичность CPU, режим, fatal/nonFatal и освобождение права управления. |
| Данные, общие для исходной и тестовой программ | В PROGRAM до загрузки и после возврата сверить H512..518, остальные сохранённые H/D, PV и флаги таймеров и счётчиков по профилю CPU. Зафиксировать расхождения до запуска исходной программы. На CPU65 особенно информативны ненулевые H512..514 и C121. Нулевая пара PV и Q сама по себе не различает сохранение и сброс таймера. |
| Входы, выходы и рабочие биты | Повторить наблюдения RUN → PROGRAM → RUN с теми же внешними входами. Сверять W/CIO с той же фазой контрольного цикла, записать входы вместе с выходами. | Состояние внутри скана и между сканами | В задачах обоих CXP найдены по два UP(521), перед RSET ON и SET L1_out_powerON, и временные TR0/TR1. TR проверять через результаты ветвей при одинаковых входах. Для UP нужен наблюдаемый результат по сканам при низком входном условии, фронте и удержании высокого условия. Учесть, что SET/RSET могут скрыть повторный импульс. При отсутствии трассы с разрешением в один скан проверку истории фронта оставить открытой. [Omron о семантике UP](https://www.ia.omron.com/support/faq/answer/26/faq01823/) |

Такой опыт различает возврат кода, параметров, наблюдаемых данных и
поведения. Историю фронтов, фазу незавершённого таймера и стек прерванного
скана имеющиеся снимки не сохраняют. Для исходной программы нужен собственный
контрольный сценарий входов и выходов до подмены и после возврата. Проверка
двух UP относится к кандидату и сама по себе не квалифицирует исходную UM.

## Основной сценарий — Windows-стенд с начала, Linux параллельно

Статус: выполняется начальный этап чтения. Доступ к обоим CPU с управляемого
Windows-стенда подтверждён. Windows используется для исследований CX-One,
Frida/Ghidra и сравнения эталонов; конечный backend сохраняет независимость.
Результаты первого этапа, исправление0306/1104 и хеши копий UM:
[отчёт только чтением](omron-hardware-readonly-2026-11-16.md).

После ручной загрузки оператором CJ1H: новый UM4604 bytes совпадает с
независимой сборкой неизменённого CXP во всём, кроме служебных слов0/1/4.
Это продвигает A.5 для конкретного CJ1H-кода; начальный2880-byte снимок
исторический. Warning при передаче всех сегментов не объяснён, другие
сегменты не проверены. См. [повторное чтение](omron-cj1h-manual-download-readback-2026-11-16.md).
Агент не выполнял запись/смену режима; доступ остаётся только чтением.

### A. Воспроизводимость и первичное чтение

1. На Windows, Linux ARM и Linux x86-64 использовать один коммит, исходники и
   JSON настроек; записать версии инструментов и хеш CLI.
2. Выполнить Omron/research и Omron CLI-тесты, vet, сборку, затем
   rewrite → compile-image → inspect-image. Сверить N1 между архитектурами.
3. Проверить identity/status по явно заданным адресам, записать маршрут и ответы.
   При неожиданной модели остановить работу с этим адресом.
4. Снять две копии UM, проверить хеши, состояние до/после и корректное завершение
   передачи. Ошибку, частичное чтение или отсутствие конечного флага не считать
   резервной копией. При изменении программы между чтениями выяснить причину.
5. Установить соответствие прочитанного UM действительно загруженному проекту
   и N1. Не угадывать преобразование и не удалять неизвестные области как padding.

Приёмка A: чтение и идентификация подтверждены отдельно для каждого CPU;
получение UM имеет отдельный результат. Подтверждение status не квалифицирует UM.

### B. Подготовка передачи без записи на действующей установке

- Подтвердить N1 → данные UM и последовательность передачи по официальному
  руководству и наблюдениям штатного CX-One. Не отправлять файл N1 напрямую,
  пока соответствие wire-формату не доказано.
- Подготовить dry-run плана передачи с привязкой к хешу образа, CPU и маршруту,
  журналом блоков и независимым чтением обратно.
  Частично реализовано: `plan-program-write` строит offline candidate0307
  блоки с хешем образа/данных иfinalbit. Привязка к CPU/маршруту, native stamping,
  полный workflow и чтение обратно ещё не квалифицированы; у команды нет
  сетевого режима. См. `omron-um-service-fields-and-write-plan.md`.
  Добавлен [офлайн-аудит](omron-cj1-offline-write-audit.md) порядка запросов,
  точных ACK и сохранённого обратного чтения. Ошибка блокирует дальнейший
  прогресс; это не живой transport/recovery или аппаратная квалификация.
- На имитаторе проверить отказ CPU, неверное подтверждение, тайм-аут и обрыв.
  После неопределённого результата записи остановиться и читать состояние;
  автоматические повтор записи и rollback не допускаются.
- Подготовить начальные данные и аудит используемых областей для испытательного
  проекта. Непонятные типы, значения и пересечения блокируют его исполнение.

### C. Будущая отдельно разрешённая стендовая запись

Обязательны изолированный стенд, отключённые исполнительные выходы, актуальные
копии программы/необходимых настроек/данных и подготовленное восстановление
оператором через CX-One. Такой резервный ПК может быть неуправляемым агентом.
Один opaque UM-файл не считать полной резервной копией контроллера.

Порядок: неизменённая программа → чтение обратно; небольшой поддержанный проект
→ чтение обратно в PROGRAM; проверенные начальные данные → детерминированный
BOOL-тест без физических выходов. Первое переключение режима выполняет оператор
явно. Не возвращать RUN автоматически, особенно после ошибки.

Затем повторить на втором CPU. Таймеры, retention, startup, несколько вызовов,
восстановление после обрыва и отключения питания проверять отдельными случаями.
Host Link имеет самостоятельную аппаратную матрицу. Результат одного CPU,
транспорта или версии не переносится на остальные автоматически.

3. При отдельно разрешённом стенде запись с Linux возможна до продвинутых
   исследований, но обычный Windows-ПК с CX-One и оператором должен быть доступен
   для восстановления. Недостающие обязательные проверки остаются блокирующими.
4. Позже подключить управляемый Windows-стенд: source-to-KBase provenance,
   D0/AC0, инициализация/размещение, wire-сравнение, новые инструкции/графы,
   прерывание передачи, retention и питание.

Переход на резервный порядок не разрешает запись на действующую установку.

## Доказательства и перенос на другую машину

Для каждой сессии создать отдельный каталог `research/hardware/<session-id>`
с manifest: коммит, ОС/архитектура/Go, хеш CLI, адреса и маршрут, исходник,
настройки, образ и хеши, сырые ответы, результаты сравнения, отказы и следующий
точный шаг. Фиксировать, был ли захват пакетов и какие области НЕ сохранены.

Начальная сессия: `research/hardware/20261116-readonly-01` в корне workspace,
вне Git-репозитория. Не объявлять её полной аппаратной приёмкой.

Передавать отдельно:

- Git с историей и переносимыми корпусами; зафиксировать последний коммит.
- `projects` и выбранные сырые `research` с SHA-256 manifest: обычный clone их
  не переносит. Сохранить исходные CXP/OPT, capture scripts и provenance.
- Для Windows-оракула — версии/хеши vendor DLL, CX-One, Frida, Ghidra/JDK,
  сценарии и необходимые результаты. Установленные приложения не переносимы
  простым копированием рабочей папки.

Доступы и секреты передавать отдельно. На новом хосте повторить offline-проверки,
сверить хеши, затем только явно разрешённое чтение. После разрыва передачи не
возобновлять запись по локальному журналу без повторного чтения устройства.
Каждый реализованный этап фиксировать отдельным коммитом и обновлять handoff.
