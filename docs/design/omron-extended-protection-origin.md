# Источник IsExtendedProtect в файловых ветвях CX-Programmer

Продолжение: [обработка OBJ и CompositeUMObject](omron-obj-protection-workflow.md).

17 ноября 2026 года статически подтверждено: в исследованных ветвях
`PLC_KBase.IsExtendedProtect` устанавливается из **локального файла**.
Найдена также запись нуля. Это уточняет
[предыдущий разбор диспетчера](omron-extended-protection-dispatch.md).
Состояние защиты действующего ПЛК этим исследованием не измерялось.

## Прямая установка и сброс

`CX-P.exe:12694ab0` получает owner, указатель на CString с путём и выходной
byte. Через MFC `CFile::Open/Seek/Read` читает четыре байта по смещению **4**.
Поворот двух halfwords и `_swab` переводят значение из big endian в native uint32.
При полном чтении оно сравнивается с пределом, выбранным из описателя PLC:

| Условие в описателе cached KBase | Предел | Выходной byte |
| --- | --- | --- |
| descriptor+44, bit20 установлен | 0x81 | 1 при равенстве, иначе 0 |
| этот bit не установлен / cached KBase отсутствует | 0x80 | 1 при равенстве, иначе 0 |

Выходной byte сначала обнуляется (`12694b60`), равенство устанавливает единицу
(`12694b9b`). Значение больше предела дополнительно обнуляет возвращаемый признак
допустимости. Не следует воспроизводить обработку ошибок открытия/короткого чтения
как независимую спецификацию: это локальная реконструкция native ветви.

Далее `12694bb6` записывает расширенный до uint32 выходной byte непосредственно
в `cached PLC_KBase+2bc`. Следовательно, это **присваивание 0/1**, а не только
накопительное включение защиты. Если кэш не инициализирован, функция вызывает
именованный `PLC_KBase::SetPLC` через `1285aa60`, затем возвращается к той же записи.
Если SetPLC неуспешен или объект отсутствует, записи нет.

Имена методов MFC разрешены по PE IAT и сохранённой в репозитории таблице
`omron/codec/testdata/mfc42-ordinals.exports.gz`; установленная MFC42 экспортирует
соответствующие функции по ordinal. DLL не загружалась для выполнения.

## Вызывающая сторона и блок 380 байт

В `124c53e0` прослежена последовательность:

1. `124c58a6` вызывает `12694ab0` с путём из локального CString и адресом byte.
2. Путь затем передаётся в `CopyFileA` (`124c58e8`). В формировании пути назначения
   участвует строка `OBJ` (`129ed4fc`); это не доказательство полного формата файла.
3. Если выходной byte ненулевой, `124c590d` вызывает `126995a0` для этой копии,
   затем при успехе `12699880`. Полная семантика последней функции ещё не разобрана.

В `126995a0` источник ранее неизвестного блока теперь установлен как CFile:

- база чтения — `0x30` либо `0x100`, по descriptor+44 bit20;
- из базы читаются **380 байт** через `CFile::Read`;
- ещё **24 байта** читаются из базы; если текущий IsExtendedProtect ненулевой,
  их смещение увеличивается на 380;
- затем вызываются помощники проверки/разбора `1284f800` и `1284f320`;
- после успешного разбора и проверки, что хотя бы одна из двух строк непуста, возможна запись
  `126997b3: [cached KBase+2bc]=1`.

У функции также есть ранний выход при descriptor+68 bit800; поэтому она
не всегда читает файл. Значения двух строк не извлекались. Обработку защищённых
данных в независимый бэкенд не переносили.

## Вторая ветвь: хвост файла и тип объекта

Вызов `124aa42d → 12699950` получает путь и объект из локального `EBP-38`.
Этот объект возвращает `124a9da0`. В нём есть две ветви:

- owner+190 → `12674e10`: уже доказанный getter cached PLC_KBase;
- при отсутствии результата — fallback owner+188, чей тип ещё не доказан.

Таким образом, принадлежность второй записи `12699a88` объекту PLC_KBase
подтверждена **для первой ветви**, но пока не для fallback. Одинаковое смещение
само по себе тип не доказывает.

`12699950` сначала вызывает `1284fc60`; его файловые помощники `12850480`
и `12850520` получают длину и читают файл через CFile. После успешной проверки
`12699950` открывает файл с флагом 2, читает последние 380 байт
(`GetLength - 0x17c`), вызывает `SetLength` с длиной без этого хвоста и разбирает
прочитанный блок через `1284f320`. При соответствующих строках записывает +2bc=1.
Это описание поведения CX-Programmer при выполнении; **мы эти функции не запускали
и никакие файлы проекта таким способом не изменяли**.

## Что это означает для независимого бэкенда

Установлен локальный источник флага и конкретное правило его обновления в одной
ветви. Нельзя пока объявлять IsExtendedProtect только свойством модели CPU,
версией драйвера или ответом контроллера. Также не доказано, что все записи поля
и все пути выполнения уже найдены.

**Смещение 4 в этом файле не квалифицировано как смещение 4 сырого N1/UM.**
В существующем разборе UM это часть служебной суммы. Смешивать два наблюдения
и выбирать 0307/0317 по такому полю readback нельзя. В соседнем валидаторе
`12693fc0` есть отдельная проверка первых четырёх байтов и константы CJ2X/CJ2M;
это дополнительная причина не переносить правило на CJ1 N1 без проверки формата.
Значение bit20 для наших конкретных CJ1-профилей в этом этапе не установлено.

Бэкенд и план передачи не менялись; `WriteQualified=false`. Сети и выполнения
vendor-кода не было. `.37` остаётся только чтение, `.36` не опрашивался.

Далее требуется:

1. Установить структуру исследованного локального OBJ/контейнера и связь с N1,
   включая источник пути в ветви `124a9de0 → 12677730` и дальнейший `12699880`.
2. Доказать тип fallback+188, проверить другие записи/копирование/сброс поля
   и значение descriptor bit20 для CJ1M CPU21 / CJ1H-H CPU65.
3. Связать результат с полным file-buffer workflow, финализацией UM и условиями
   выбора сервиса. Аппаратную запись пока не квалифицировать.

синтетических проверок преобразования endian. Это статические проверки и
