16 ноября 2026 года. Пользователь гарантировал окно без сторонних изменений
на `.37`. Агент использовал только чтение CJ1H10.0.174.37; `.36` не опрашивался.
Деактивация исполнительных механизмов не объявлена, запись/смена режима запрещены.

## Прочитанный образ

UM2716 bytes, SHA-256
`d54d9fcb0e4c5f6fb95bc16c31b07fd55a880982835d31b6676af744a1c34a46`.
Совпадает с предыдущими двумя копиями после занятия. Одна задача256, без FB,
24 слова инструкций. Начало code body: word654 полного файла. Сырые байты
имени: `cdeee2e0ffc7e0e4e0f7e031`, исходная кодировка автоматически не назначалась.
До и после файловых запросов CPU сообщил status5, mode4, fatal0, nonFatal0.

Все24 слова разобраны в18 инструкций существующим квалифицированным кодеком
для явно выбранных CJ1H-H CPU65/BCD. Каждая инструкция закодирована обратно
и точно совпала со своими исходными словами. Неизвестных хвостов в этой задаче нет.

```text
LD 0.05
LD 0.04
CNT 120 #0002
LD 0.03
LD 0.07
CNT 121 #0003
LD C121
OUT 4.08
OUT W0.01
LD C120
OUT W0.02
OUT 4.10
LD W0.01
OR W0.02
OUT 4.14
OUT 4.12
CMP(020) #DEAD #DEAD
END
```

Список показывает числовые операнды, не назначения физических сигналов.
CMP сохранён как инструкция; без исходника не утверждается, что это был
редакторский разделитель, а не пользовательская команда. LD-графика, номера
исходных рунгов/секций, имена символов и комментарии не восстановлены.
Полное покрытие декодером не доказывает корректность исполнения или установку
конкретных физических модулей. BCD-профиль не заменяет точную unit-version матрицу.

## API и CLI

Добавлены `um.N1Image.DecodeTasks` и флаг:

```sh
naut omron inspect-image -decode-tasks -model "CJ1H-H CPU65" -timer-mode bcd program.bin
```

Можно сочетать с `-function-blocks` и `-decode-fb-bodies`. Отчёт содержит
code/image-relative offsets, исходные words и mnemonic, coverage, stop reason
и весь opaque tail. На первой неизвестной форме задача останавливается:
поиск похожего opcode внутри операндов и попытки перескочить неизвестные слова
не выполняются. Частичный разбор не выдаётся за полный. Каждая выданная
инструкция проходит точное обратное кодирование; несовпадение блокирует отчёт.

Число декодированных инструкций ограничено65536 суммарно по образу. Даже при
исчерпании лимита остаток сохраняется как opaque tail. API повторно читает
неизменённые retained bytes, а не изменяемые публичные diagnostic поля Tasks.
Требуется явный BCD и поддержанный model; binary header flag отклоняется.
`sourceRestored`, `symbolNamesRestored`, `hardwareQualified` остаются false.
FB-definition bodies этим флагом не декодируются.

## Цикл через независимый компилятор

Из списка создан диагностический однораздельный CXT с явным ASCII именем
`RecoveredTask256`, пустыми symbol/FB таблицами и сохранённой инструкцией CMP.
Это производный тестовый исходник, не оригинальный проект контроллера.
Он собран обычным `compile-image` с явным no-FB JSON, без vendor DLL/CX-One.

Результат2716 bytes, SHA-256
`248325f200561d8072ef0e862e632be9189eeb5f82ca503643131ab23972d902`.
Все24 слова тела задачи совпадают точно. Сравнены также все байты полного файла:
различия только в служебных словах0/1/4 и шести packed-name словах619–624,
где имя заменено явно. Task configuration, directory, обёртки, длины и остальные
поля совпадают; нормализация неизвестных слов не выполнялась.

Неизвестные служебные поля live→generated:
0:00003f74→00000000,1:00004477→00000000,4:0000002b→00000000.
Их назначение и правила записи не квалифицированы. N1 не передавался на CPU.

## Проверка доступа к сохранённым файлам

Документированным2201 FILE NAME READ запрошено не более20 записей корня
каждого носителя:8000 memory card и8001 EM file memory. Оба запроса вернули
end code2301. По W342 это File device missing: указанный носитель не существует
как файловое устройство. Ни файлов, ни таблицы символов так получить не удалось.
Это **не доказывает отсутствие символов во всех внутренних областях CPU**.
Поддержка отдельного comment/source memory ещё требует исследования.
Никакого форматирования, создания носителя, снятия защиты или повторов записи
для обхода отказа не выполнялось.

Дальше исследовать физическую Basic I/O конфигурацию отдельно от регистрации,
внутреннее хранение символов/исходников и неизвестные служебные поля. Совпадение
предыдущей I/O registration table не закрывает эти вопросы. Независимая загрузка,
инициализация данных и аппаратное исполнение остаются незавершёнными.
