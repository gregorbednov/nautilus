# Путь загрузки программы через CX-Server

Статическое исследование 17 ноября 2026 года, после `ba8a1b7d`.
Сетевых обращений к ПЛК, запуска vendor-кода и изменения установки не было.
Разрешение на действующей установке остаётся **только чтение**; `.36` offline.

## Что подтверждено

Прослежена цепочка от CX-Programmer до обработчика коммуникационного сервера:

```text
CX-P.exe:12610780
  call12610ab3 → thunk12859810 → IAT12b24518
  cdmapi32.dll ordinal14 = CDMDownloadProgram:6000534d
  → inner6001fe08
  → ICXSCommunications vtable slot0x14
  cdmsvr20.exe:004395f9
  → callback type5 constructor0044c162
  → common dispatch00431bcc
```

Последние два адреса найдены в серверном обработчике; их внутренняя реализация
в этом этапе ещё не исследована. Это статически достижимая ветвь, а не запись
реальной передачи или доказательство выбранного CPU/драйвера.

### Граница CX-Programmer → CDM

Единственный найденный относительный вызов импорта `CDMDownloadProgram` в
исполняемых секциях данной версии CX-P находится по `12610ab3`. Он принадлежит
функции `12610780`, использующей автомат состояний нескольких операций передачи.
Это не исключает косвенные вызовы, которые поиск относительных CALL не покрывает.

В найденной ветви передаются:

- PLC handle из поля объекта `+0x74`;
- исходное имя файла из `+0x78`;
- нулевые destination filename, end mask и mask length;
- callback `1260f4a0` и контекст объекта.

Назначение первых семи параметров подтверждено строками логирования **самой
библиотеки**, а аргументы — ассемблером вызывающего участка. Строки:
`hPLC`, `lpszSrcFilename`, `lpszDestFilename`, `lpEndmask`, `wMasklen`,
`lpDownlProc`, `lParam`. Дополнительную stack-константу `12a2c10c` не считаем
восьмым параметром API без отдельной проверки соглашения о вызове.

Нельзя пока утверждать, что путь `+0x78` всегда обозначает тот же N1, который
выдаёт наш компилятор: происхождение файла и предшествующая подготовка остаются
следующей частью трассировки. Есть и альтернативная ветвь `12613480`, выбираемая
предикатом `126992e0`; её смысл и соответствие CJ1 не установлены.

### Запрос внутри CDM

`6001fe08` проверяет непустое исходное имя, открывает файл для чтения и закрывает
его. В видимом участке содержимое UM не читается и контрольные поля не считаются.
Далее выделяется внутренний parameter block с кодом `9` и длиной данных `0x20b`.
В данные копируются исходное и конечное имена (второе по offset `0x104`),
а длина маски записывается по `0x208`; ненулевая маска обрабатывается отдельно.
Для найденного CX-P вызова эта маска нулевая.

Общий helper `6003eff1` создаёт заголовок из четырёх little-endian 16-bit полей:
`ffff`, `dataLength+4`, `operation`, `dataLength`; данные следуют после 8 байт.
Это **внутренний запрос CX-Server**, не FINS `0307` и не описание сетевого пакета.

Перед вызовом vtable slot `0x14` устанавливаются callback type `5`, callback,
пользовательский контекст и дополнительные служебные поля. Статическая цепочка
инициализации `6000bb1c → 60025e80` создаёт:

| Назначение | GUID |
| --- | --- |
| Communications Class | B76F5410-3E8A-11D3-85A9-005004606465 |
| ICXSCommunications | E09519B0-3E84-11D3-85A9-005004606465 |

В 32-bit регистрации Windows этот класс указывает на `cdmsvr20.exe`. Регистрация
читалась без создания COM-объекта. Наличие регистрации само по себе не является
записью фактического исполнения этой ветви.

### Соответствующий серверный метод

GUID интерфейса найден также в server map по `0048cd78`. Object map содержит
CLSID по `00476280`; цепочка фабрики `00453340 → 004539d0 → 00455b60` устанавливает
vtable `00475764`. Её элемент `+0x14` равен `004395f9`.

Этот обработчик проверяет PLC handle и доступность связи, выбирает объект по
типу callback. Для type `5` вызывает конструктор `0044c162`, затем общий
`00431bcc`. Последующая маршрутизация к модели CPU, пакетам и драйверу ещё
не установлена.

## Исправлен экспорт доказательств Ghidra

В режиме `-noanalysis` декомпилятор нашёл блоки за пределами первоначального
listing function body. Старый `ExportCJ1Functions.java` сохранил лишь **135**
инструкций, хотя pseudo-C содержал значительно больше; вызов `12610ab3` отсутствовал
в assembly/calls JSON. Простого переноса сбора assembly после декомпиляции оказалось
недостаточно: listing body не расширился автоматически.

Теперь экспорт объединяет listing body с basic blocks из high function,
дизассемблирует их начала и собирает инструкции/ссылки по объединению адресов.
Добавлено поле `instructionScope`, описывающее этот охват. Повторный экспорт
той же функции содержит **1430** инструкций и ссылку
`12610ab3 → 12859810`. Это исправление полноты исследовательского отчёта,
не квалификация декомпиляции и не изменение компилятора Nautilus.
Старые отчёты не переписывались: при опоре на отсутствие вызова в старом отчёте
нужно сначала проверить покрытие соответствующего участка.

## Что остаётся

Различие между resident quantum **256** в исследованном виртуальном CPU и
наблюдаемым real-UM отношением `ceil(bytes/64)` **не объяснено**. Не установлены
переходы файла в FINS, stamping заголовка у отправителя, реальный CPU-family
selector, правила ACK/ошибок и восстановления после прерывания передачи.
`NativeAlgorithmConfirmed`, `WireImageMappingQualified` и `WriteQualified`
остаются false. Продуктового writer/stamping API не добавлено.

Далее: исследовать `0044c162`/`00431bcc`, связать создание исходного файла с
вызовом CDM и проследить выбранный CPU-драйвер до `0307`. Результат сопоставить
с [предыдущей финализацией UM](omron-um-native-sums-and-finalization.md), сохраняя
различие между виртуальным CPU, внутренним запросом CDM и реальным FINS wire.
