# CJ1: PnP-ветвь и транзакция загрузки программы

Продолжение: [различие стандартного0307 и расширенного0317 сервисов](omron-program-service-versions.md).

Исследование 17 ноября 2026 года после `10fdfb26`. Все действия локальные:
чтение файлов/регистрации и статический анализ Ghidra. Vendor API не запускались,
сети и записей в ПЛК не было. `.37` остаётся только чтение, `.36` offline.

## Выбор ветви: legacy-сценарий пока не относится к CJ1

В продолжение [серверной цепочки](omron-cj1-native-transfer-path.md) исследованы
`CDownloadReply` (`0044c162`) и `CCommandMessage` (`00412230`). Командный объект
копирует исходный запрос в собственный буфер. Его методы обращаются к интерфейсу
выбранного устройства: получение сценария, начало и продолжение обработки.

`DevInterfaceTranslator.dll` разделяет создание устройства на две ветви:

- `60e01545 → 60e0186f`: legacy, через `CXStatic.dll`;
- `60e01545 → 60e023b1`: PnP, через менеджер устройств.

Предикат `60e0d3dc` извлекает `DEV` из конфигурации и ищет
`COMPONENTS\DeviceConfigurations\<DEV>` в менеджере категорий. Успешный поиск
соответствует PnP-ветви. Это статический анализ, не запись фактического исполнения.

Независимый парсер Nautilus прочитал исходные проекты:

| Проект | DEV | CPU | Категория установленной конфигурации |
| --- | --- | --- | --- |
| CJ1H | CJ1H-H | CPU65 | DeviceConfig.CJ1H_HConfig.1 |
| CJ1M | CJ1M | CPU21 | DeviceConfig.CJ1MConfig.1 |

Обе категории существуют в 32-bit
`HKLM\SOFTWARE\OMRON\Category Manager\COMPONENTS\DeviceConfigurations`.
Их CLSID ведут в
`C:\Program Files (x86)\Common Files\Omron\Drivers\CXSDI_CS1Config.dll`.
Наличие регистрации не доказывает работоспособность класса или сетевой обмен.

В legacy-ветви восстановлен поиск сценариев `CXStatic.dll:60c08757` и базовые
операции чтения базы: little-endian uint16/uint32, byte и строка с byte-length.
Заголовок `CDMPLC.DAT` содержит смещения таблиц; категория `3` с флагом
`02000000` ссылается на сценарий `202`. Выбор варианта учитывает первичный CPU-key,
резервный group-key, маску `80ffffff` и дополнительные биты `24..30`.

Отдельный разбор базы воспроизвёл **50** групп устройств до границы таблицы.
Отдельных `CJ1H-H`, `CJ1M`, `CS1`, `CS1H` среди них нет. Строки CJ1, найденные
в других частях файла, сами по себе не определяют конфигурационную группу.
Поэтому **сценарий 202 не квалифицирован для CJ1** и не переносился в бэкенд.
Его исследование сохраняется как проверка альтернативной ветви.

## Найдены компоненты современного пути

В каталоге Common Files найден `CXSDI_CS1Comms.dll`. Он импортирует реализацию
`ParallelCommunication` из `C:\Windows\SysWOW64\CXSDI_CS1BaseComms.dll`.
`RequestMessageService:61a0dbc0` вызывает `ServiceGenerator:61a14110`.
Генератор получает идентификатор из сообщения и выбирает реализацию сервиса.
Полная связь модели/версии CPU с конкретной регистрацией сервиса ещё не закрыта.

В `SysWOW64` найдены `CXSDI_SeriesCS1MessageServices1..17.dll`, включая реальные
классы программной передачи. В `...Services1.dll` исследованы:

кандидаты адресов; например, `63018fa0` — исключительный путь, не обычный
конструктор. Он не служит основанием для формата передачи.

## Что видно в нативной транзакции

`63019140` создаёт команду следующего вида:

```text
03 07 | program:u16 BE | offset:u32 BE | count:u16 BE | data[count & 7fff]
```

Успешно связаны следующие признаки:

- непосредственные записи `03` и `07` в начале запроса;
- порядок байтов номера, смещения и длины;
- выравнивание размера блока через `& fffc`;
- уменьшение последнего блока до остатка;
- состояние `2` означает последний блок и включает `8000` в длину;
- данные копируются из сохранённого буфера с текущей позиции;
- при нулевом end code обработчик читает uint16 BE по offset `6` данных ответа
  и прибавляет подтверждённую длину к позиции;
- при ненулевом end code формируется ошибочный результат вместо обычного
  продвижения.

Это подтверждает общий формат уже существующего offline-планировщика `0307`.
Функция подготовки блока **не доказывает** максимальный размер `996`: этот лимит
планировщика по-прежнему основан на ранее проверенном W342.
Не доказаны выбранная версия сервиса для каждого CJ1, полная подготовка файла,
stamping UM и поведение физического CPU. Отношение real-UM `ceil(bytes/64)`
к resident quantum `256` в симуляторе остаётся открытым.

## Реализована независимая проверка ответов

Добавлен чистый Go API:

```go
transfer.ValidateProgramWriteResponse(requestPayload, responseBody)
```

`requestPayload` не содержит FINS header/command; `responseBody` содержит
command, end code и данные, но не FINS header. Функция проверяет структуру
запроса, выравнивание и переполнение следующего смещения, затем требует:

- команду `0307` и нулевой end code;
- ровно 8 байт данных успешного ответа;
- номер программы `ffff` и исходное смещение;
- точное подтверждение всей запрошенной длины без last-bit в ответе.

Возвращаются подтверждённая длина, следующая позиция и `FinalRequested` — признак
**запроса** последнего блока. При любой ошибке результат нулевой, end code
сохраняется в диагностике. Нулевое продвижение означает отсутствие принятого
подтверждения, а не доказательство отсутствия изменений на ПЛК.

Эта строгая политика сопоставления — наша проверка; нативный decoder выше
использует подтверждённую длину и сам по себе не доказывает все эти проверки.
API работает только с переданными bytes: без соединения, повторов, переключения
режима или отправки. SID/route сопоставляет будущий транспортный workflow.
ACK не доказывает завершённую загрузку, сохранность UM или правильность
исполнения; необходимы отдельное чтение обратно и аппаратная квалификация.

Синтетические тесты проверяют обычный/последний блок, сохранность входных bytes,
чужую команду/program/offset, partial/zero/excess count, end codes, усечение,
лишние bytes, переполнение и некорректные запросы. Это не реальные PLC ACK.
Прошли scoped Omron/research tests, Omron CLI tests, vet и сборка Nautilus.
