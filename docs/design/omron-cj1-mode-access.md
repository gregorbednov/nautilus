# CJ1: команды режима и права доступа, свежие копии обоих CPU

18 ноября 2026 года. Реализованы низкоуровневые mutating Go API в `omron/fins`.
Команды управления проверены только на localhost/тестовых Transport. На настоящих
CJ1H/.37 и CJ1M/.36 выполнено только чтение: 0501,0601,0306; без 0401/0402,
0C01/0C02/0C03, записи программы, смены защиты или настроек. CLI остаётся читающим.

## Контракт команд

| Go API | Command DATA | Значение успешного ответа |
| --- | --- | --- |
| `RequestCPUMode(ctx, CPUModeProgram)` | 0402 + FFFF | ACK STOP; фактический PROGRAM подтвердить отдельным Status |
| `RequestCPUMode(ctx, CPUModeMonitor)` | 0401 + FFFF + 02 | ACK MONITOR; этот режим исполняет программу |
| `RequestCPUMode(ctx, CPUModeRun)` | 0401 + FFFF + 04 | ACK RUN; этот режим исполняет программу |
| `AcquireProgramAccess(ctx)` | 0C01 + FFFF | ACK обычного, не принудительного получения права |
| `ReleaseProgramAccess(ctx)` | 0C03 + FFFF | ACK глобального освобождения права, независимо от владельца |

Неявные варианты0401 без mode, которые W342 трактует как MONITOR, не используются.
Неизвестный mode отклоняется локально. Предварительно отменённый context не
отправляет запрос и не портит клиент. На успешном ответе DATA должно быть пустым;
ACK с дополнительными байтами, ошибкой маршрута/SID/command, неверным размером,
ненулевым end code или транспортной ошибкой закрывает и навсегда останавливает
клиент. То же terminal правило действует для raw Call с0401/0402/0C01/0C02/0C03.
Обычные read end codes по-прежнему не портят сеанс:0306 может уменьшить размер
чтения при1104. Повторов, reconnect и автоматических управляющих команд нет.

При коррелированном ответе0C01/3001 ровно три DATA bytes декодируются как
network/node/unit другого владельца. `AccessRightBusyError` сохраняет адрес и
оборачивает исходный `EndError` для errors.As. Неверный SID/route/command или
неполный owner не превращаются в подтверждённый адрес владельца. Ненулевой end
code сохраняется и при отсутствии корректных owner bytes. Успешный0C01 с owner
DATA не принимается за получение права. Typed helper для force acquire0C02 не добавлен.

## Существенное ограничение владения

W342 5-3-26 прямо определяет0C03 как освобождение права независимо от текущего
владельца: команда может затронуть другое устройство. Поэтому Close, ошибка и
потеря ACK никогда не вызывают RELEASE. Само получение нормального ACK0C01 не
является lease: другой узел может принудительно получить или глобально освободить
право, не сообщив прежнему владельцу. Закрытие TCP не подтверждает освобождения;
новый negotiated source node не наследует подтверждение старой сессии.
Поведение настоящего CPU при разрыве TCP в этом этапе не исследовалось.

Локальный adversarial peer специально сохраняет владельца после EOF и выдаёт
3001 новой TCP-сессии: клиент не отправляет force/release/retry. Это проверка
отсутствия предположений в коде, а не доказательство поведения настоящего CJ1.

## Основание форматов

Использован локальный `research/W342.pdf`: 5-3-13/14, печатные189-190
(PDF211-212); 5-3-24/25/26, печатные202-206 (PDF224-228); end code3001 —
печатная161 (PDF183). Извлечены тексты и визуально проверены схемы0401/0C01,
различие0C02 и глобальная семантика0C03. На печатной203 есть противоречивые
скопированные comments, включая номер0C01 у forced acquire; реализация следует
заголовкам, схемам и таблицам, которые различают0C01 и0C02.
Это документальная проверка, не новая трассировка CX-One или аппаратная приёмка.

## Проверки и следующая реализация

Добавлено7 top-level tests: явные payload/ACK, ошибки и terminal state,
диагностика busy owner, local cancellation/validation, raw Call и сохранение
read semantics. Localhost TCP проверяет обе модели: identity, обычный acquire,
PROGRAM/status, MONITOR/status, RUN/status, явный release, identity и EOF без
скрытой команды. Тестовый peer не исполняет N1 и не моделирует финализацию CPU.
Все10 пакетов Omron, Omron CLI tests и go vet прошли; Go1.26.10, Windows amd64,
CGO_ENABLED=0, зависимости offline. Аппаратные mode/access команды не проверены.

Следующий шаг — связать эти wire API с выделенной ProgramSession и журналом:
сохранять попытку/результат каждого control шага, проверять target и status,
управлять правом на том же соединении до его явного завершения, отдельно
согласовывать доступ для новой сессии возврата. Сейчас ProgramSession закрывает
соединение после candidate/readback, поэтому композиция Acquire→ProgramSession
не является завершённым access lifecycle. RELEASE после потери соединения и
автоматический RUN не добавлять. При3001 останавливаться с диагностикой владельца.
После интеграции и локальных fault tests подготовить отдельный опыт на CJ1H,
начиная с проверки режима/доступа и сравнения исходных байтов; перед0307 остаются
защита/выбор сервиса, profile/finalization, backup вне программы и процедура возврата.
Операторское подтверждение изоляции уже относится к обоим CPU; повторять его не нужно.
