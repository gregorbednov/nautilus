# CJ1: от файла полного образа к байтам блоков передачи

18 ноября 2026 года. Продолжение [пути CX-Server](omron-cj1-native-transfer-path.md)
и [обычного writer N1](omron-n1-writer-and-protected-file.md).
Исследование статическое: Ghidra и чтение закреплённых PE-файлов. Vendor API
не вызывались, сетевых обращений к ПЛК не было. Действующая установка остаётся только для чтения.

## Результат и границы

Для исследованной стандартной ветви восстановлена связь имени файла и данных:

```text
CX-P:124ad800 / 124afc30
  выбранный KBase+2ce8 → локальный CString -74 / -60
  → первый аргумент 12678530 / 12679340
  → третий аргумент конструктора 1260f030
  → CString объекта передачи+78
  → ранее исследованный 12610780 → CDMDownloadProgram
  → CReadStatusTransaction:630385e0, файл с начала
  → vector+0xb0, begin+0xb4 / end+0xb8
  → getter63038350 → service vector+38
  → standard transaction Init63019460(base=0, capacity, vector)
  → 63019140: data = vector.begin + progress, длина = текущий блок
```

Сервисная часть копирует прочитанный файл целиком. Ни getter, ни Init, ни
сборщик0307 не снимают48-byte OBJ prefix, не пересчитывают заголовок N1 и не
переставляют байты тела. Сериализация N1 в big endian выполнена writer ранее;
здесь данные копируются MOVSD/MOVSB. Это статическое доказательство конкретной
ветви, а не захват реальной передачи или квалификация всей загрузки на CPU.

Локальная plain OBJ-обёртка — отдельный формат. Её prefix не должен попадать в
raw N1 план передачи. Новая регрессия на обоих CPU fixtures проверяет отказ
`PlanProgramWrite` для OBJ; после явного `ParsePlainN1Object` планы совпадают с
планами исходного N1 полностью. Автоопределения формата и сети нет.

## Происхождение имени и корректный разбор стека

`124ad800` копирует CString по выбранному KBase+2ce8 в local-74, затем передаёт
его первым аргументом12678530. Второй обработчик124afc30 делает то же через
local-60 и12679340. Выбор модели проходит124a9da0: текущая модель либо fallback
из+188; это не наблюдение реального состояния ПЛК.

В обеих обёртках входной filename становится третьим аргументом1260f030.
Проверка рассчитывает размеры кадров из прологов:468/2c4 bytes. С учётом PUSH
загрузка EDX по12678fac/126798de соответствует entryESP+4. Этот EDX передаётся
третьим аргументом конструктора, который читает entryESP+0c и присваивает
CString+78 через1285af34.

Здесь важен импорт1285ace8: `PLC_KBase::HasAccessRights()` без явных аргументов.
Предшествующие ему PUSH остаются аргументами последующего конструктора.
Считать этот вызов getter имени или функцией, снимающей четыре аргумента,
нельзя. Импорты CString также разрешены:1285af82 — copy constructor
(MFC ordinal535),1285af34 — присваивание char*. Версионная таблица MFC сохранена
в переносимом исследовательском корпусе проекта.

## Предварительная обработка и защита

В обработчиках есть вызов126994d0 с именем файла. Повторная проверка показывает:
при отсутствующей выбранной модели либо нулевом KBase+2bc helper возвращает
успех без1284f970. Поле+2bc ранее связано именованными экспортами с
`IsExtendedProtect`; см. [разбор защиты](omron-extended-protection-dispatch.md).

При ненулевом флаге вызывается уже исследованная цепочка1284f970→1284f9e0
с подготовкой защищённого файла. Свежий разбор1284f970 согласуется с прежним:
time/srand/rand и вызов1284f9e0. Она не исполнялась, секреты не извлекались,
реализация защиты не добавлялась. Поэтому вывод о raw N1 относится к обычной
ветви с отключённой extended protection и неподходящ для общего0317 workflow.
Также отдельно остаётся ULC-конверсия writer, не квалифицированная для CJ1.

## Из Init нельзя выводить удаление начала файла

Декомпилятор неправильно восстановил часть аргументов Init и показывает
`unaff_retaddr`. Ассемблер и вызывающий участок дают три явных аргумента:
base offset, вместимость команды, ссылка на vector. Начальный base здесь нулевой.
Init копирует vector полностью, сохраняет полную длину и выравнивает размер блока.

Vtable стандартной транзакции630456d4:

| Slot | Метод | Назначение |
| --- | --- | --- |
| +2c | 63019460 | Init |
| +40 | 63019780 | Вычесть10 из вместимости команды |

Slot+40 не возвращает буфер. Из10 bytes складываются command2 и поля
program2/offset4/count2. Данные в сформированной команде начинаются с+0a.
Это не10 bytes N1 и не48 bytes OBJ. Связь расширенного Init63018c20 с его
vtable63045674 также проверена;0307 план не объявляется реализацией0317.

## Проверки реализации

Повторный полный `go test -buildvcs=false -mod=readonly -timeout 180s ./omron/...`
прошёл во всех девяти пакетах; общий `go vet -buildvcs=false -mod=readonly
./omron/...` также завершился успешно. Загрузка зависимостей была отключена
через GOPROXY=off и GOSUMDB=off. Предыдущая задержка не повторилась; её причина
не установлена. Статическая проверка125/125 и повторная генерация корпуса
также успешны. Аппаратная квалификация этим прогоном не выполнялась.

## Что дальше

Путь чтения/копирования файла закрыт статически для исследованной ветви.
Остаются выбор стандартной ветви для конкретного CPU/unit version, допустимая
вместимость, исключение неподдерживаемых вариантов входного файла и полная
финализация служебных слов0/1/4. Различие real64/simulator256 не объяснено.
Далее — профиль CPU/финализация, затем автомат передачи, неопределённый исход,
обратное чтение и восстановление. Успешный ACK не равен успешному исполнению.
`WireImageMappingQualified=false`, `WriteQualified=false`; writer API и разрешение
на аппаратную запись не появились.
