# N1 writer и отдельная подготовка защищённого файла

Продолжение: [разделение task/full-program и уточнение границ функций](omron-task-versus-program-dispatch.md).

17 ноября 2026 года. Продолжение [файлового workflow OBJ](omron-obj-protection-workflow.md).
Проверены две отдельные цепочки: `CompileMultipleProgramsAndProduceBinaryFile`
в CX-Pdata.dll и вызывающие `EncryptUMObject` функции CX-P.exe.
Полученные факты не дают основания добавлять обёртку или шифрование ко всем N1.

## Обычная запись N1

Именованный writer `PLC_KBase::CompileMultipleProgramsAndProduceBinaryFile`,
VA `121c28ef`, выбирает путь из явного аргумента либо `KBase+2ce8`;
есть также ветвь временного файла. Поэтому найденное ранее `+2ce8` действительно
используется как путь результата компиляции, а не только как произвольная строка.

В прослеженной N1-ветви:

- буфер из `0x14a=330` dwords сначала обнуляется (`121c4f32` — предел цикла);
- затем заполняются flags и остальные поля, начиная с индекса6;
- при выборе всей программы (`param6=ffff`) writer передаёт в
  `N1WriteToArchive` заголовок длиной `0x528=1320` bytes (`121c576d/121c5786`);
- далее записываются дополнительные данные, каталог задач и тела через тот же
  сериализатор. N2 остаётся отдельной ветвью с selector bit20.

Именованный `N1WriteToArchive`, VA `121c632d`, переставляет байты каждого
32-bit слова и записывает результат в буфер CArchive. Входная длина задаётся
в байтах, цикл обрабатывает полные слова. На little-endian x86 итоговые байты
идут в **big endian**, как у наших сохранённых compiler N1.

Независимый Python replay этого арифметического цикла воспроизвёл оба файла
по4592 bytes целиком: **2296 dwords** суммарно. Дополнительно проверены7
граничных/синтетических значений, включая старший bit и ffffffff.
Это replay сериализации уже известных слов, а не повторная компиляция проекта.

В двух образцах первые6 служебных слов нулевые. Writer не превращает их здесь
в наблюдаемые аппаратные суммы. Отдельного заголовка контейнера перед этим N1
в прослеженной обычной ветви не установлено; полный workflow после writer
всё ещё требует проверки.

## Уточнение ветви +280: это ULC

После закрытия архива при `KBase+280 != 0` вызывается `121d3ef3`.
PE export однозначно именует функцию:
`PLC_KBase::ConvertUMObjFromCJToULC`.

Она создаёт/использует объект из поля+284 и вызывает внутренний `1224a600`.
Это не найденный общий writer защиты и не доказательство, что каждому CJ1 N1
нужен дополнительный контейнер. Ветвь ULC исключена из объяснения обычной
упаковки, пока не будет установлена её применимость к конкретному профилю.

## Симметричная цепочка EncryptUMObject

PE export CX-P.exe:
`?EncryptUMObject@CEncryption@@QAEJPAKKKK0@Z`, VA **12859ac0**.
Его вызывает `1284f9e0` по `1284fb35`. Прослежено:

```text
126994d0 — проверяет cached KBase.IsExtendedProtect
  → 1284f970 — формирует начальное значение через time/srand/rand
  → 1284f9e0 — читает файл, переводит данные в слова
  → CEncryption::EncryptUMObject (12859ac0)
  → 128505d0 — записывает полученные bytes в файл
```

При нулевом IsExtendedProtect `126994d0` возвращается с успешным исходным
результатом, не вызывая `1284f970`. Это подтверждённый gate именно этого caller,
не универсальное правило всех путей.

`128505d0` открывает файл через CFile с флагом1, ищет начало и вызывает
`CFile::Write` через `1285b9ea`, затем закрывает файл. Новый размер не задаёт;
приписывать helper семантику усечения файла нельзя.

Есть второй caller `12699520`, который также вызывает `1284f9e0`.
Перед вызовом обрабатывает один числовой аргумент: при нулевом третьем stack
аргументе и сброшенном descriptor bit20 уменьшает значение на0x400, затем
устанавливает bit0x8000. Смысл этого аргумента пока не квалифицирован;
не считаем его автоматически длиной, адресом или PLC-версией.
Статические direct-call кандидаты `12699520`: `124da2b3`, `124e28da`, `12612097`.
Это точки следующего анализа, а не уже доказанные полные workflows.

Декомпилятор плохо восстанавливает сигнатуру `1284f9e0` и аргументы через
регистры; строки pseudo-C с `unaff_*` не принимаются за спецификацию API.
Значения паролей не извлекались, native encryption не исполнялся и не переносился.

## Что остаётся

Найден путь compiler N1 и отдельный путь шифрования файла. Не установлены:

1. Где именно вставляются380 bytes и записывается marker80/81, прочитанный
   предыдущим валидатором `12694ab0`.
2. Как обе цепочки соединяются с полной подготовкой файла перед service3/532.
   Вызов `12612097` находится в отдельном helper12611fd0, вызванном из диспетчера;
   последующий разбор установил task-сервисы463/526 (см. продолжение).
3. Тип fallback+188, привязка descriptor bit20 к целевым профилям и соответствие
   защищённого локального файла реальному UM.

Не нужно получать секреты или реализовывать защиту, чтобы продолжить обычный
путь flag0. В первую очередь следует проследить его до передаваемого буфера.
`WriteQualified=false`; бэкенд в этом этапе не менялся.
