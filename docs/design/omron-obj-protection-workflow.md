# OBJ после определения extended protection

Продолжение: [N1 writer, ULC и отдельная цепочка EncryptUMObject](omron-n1-writer-and-protected-file.md).

Продолжение [исследования источника флага](omron-extended-protection-origin.md),
17 ноября 2026 года. Прослежен вызов `12699880` после `126995a0`:
он вычисляет область локального файла и передаёт её в
**`CEncryption::CompositeUMObject`**. Это дополнительная операция файлового
workflow, которую нельзя автоматически применять к сырым N1.
Полный формат OBJ и его соответствие wire image пока не доказаны.

## Что делает вызывающий код

В `124c53e0` нулевой byte результата `12694ab0` ведёт через `124c5904`
непосредственно к `124c597c`, минуя обе функции `126995a0` и `12699880`.
Ненулевой byte ведёт сначала к разбору блока защиты, затем, при успехе,
к `12699880`. Это установленный порядок именно этой ветви; другие вызовы
могут иметь дополнительные условия.

`12699880` получает длину из `12694810`, выбирает базу `0x30` либо `0x100`
по descriptor+44 bit20 и добавляет `0x17c=380`, если cached
IsExtendedProtect ненулевой. Затем вызывает `12850100(path, length, offset)`.

| База | IsExtendedProtect | Смещение начала области, bytes |
| --- | --- | --- |
| 0x30 | 0 | 48 |
| 0x30 | ненулевой | 428 |
| 0x100 | 0 | 256 |
| 0x100 | ненулевой | 636 |

Это смещения внутри исследуемого локального файла, не адреса памяти ПЛК
и не смещения блоков FINS.

## Как вычисляется длина

`12694810` читает четырёхбайтное поле файла и приводит big endian к uint32:

- при сброшенном descriptor bit20 — offset `0x0c`; если поле нулевое,
  пробует offset `0x08`;
- при установленном bit20 — offset `0xdc`, затем при нуле последовательно
  `0xe0` и `0xe4`;
- при ненулевом поле и включённом IsExtendedProtect вычитает **380 байт**;
- если результат нулевой, использует `CFile::GetLength - effectiveOffset`.

Единицы подтверждены потребителем: выделение буферов и CFile::Read используют
это значение как число байт. В Ghidra pseudo-C локальное значение ошибочно
типизировано как указатель, поэтому вычитание выглядит как `param_2 - 0x5f`.
Машинная инструкция `12694994` — **SUB [EBP+8],0x17c**, а не вычитание95 байт.
Полную обработку повреждённых файлов и ошибок чтения пока не переносим.

## Обработка полезной области

`12850100` открывает файл с флагом2, выделяет два буфера указанной длины,
читает область с effectiveOffset и собирает uint32 big endian из её байтов
`0x14..0x17`. Затем:

```text
12850100
  → 1284ff00        byte/word conversion
  → 12850070       wrapper
  → 12859af0       exported CEncryption::CompositeUMObject
  → 1285a430       internal implementation
```

Именованный PE export:
`?CompositeUMObject@CEncryption@@QAEJPAKKK00@Z`, VA `12859af0`.
Его тело — внутренний адаптер аргументов с вызовом `1285a430`, а не импорт
через FF25/IAT. Поэтому прежняя неудача поиска импортированного имени
не свидетельствует об отсутствии именованной функции.

`1284ff00` переводит длины в число четырёхбайтных слов и конвертирует endian
буферов. `12850070` передаёт начальное смещение0 и считает native result0
успехом. При успехе верхний обработчик ищет то же файловое смещение и вызывает
**CFile::Write** (`128501ba → 1285b9ea`, MFC42 ordinal6385).

В `1285a430` для начального смещения0 требуется минимум6 слов. Шестое слово
используется как начальное состояние; при нуле функция возвращает `fffffffe`.
В ненулевой ветви видны XOR/rotations и вызовы `1285a800`/`1285a680`, включая
обработку блоками до `0x400` слов. По этому фрагменту не даём алгоритму
стандартного криптографического имени и не переносим его в бэкенд.

У двух сохранённых compiler N1 (`cj1h-baseline.n1`, `cj1m-input-bit.n1`,
оба4592 bytes) word5 равен0. Это отдельный проверенный факт; он не доказывает,
что буфер из OBJ уже является таким N1. Применять найденную обработку
безусловно ко всем нашим образам было бы необоснованно.

## Путь второй ветви и отвергнутый shortcut

В `124a9de0` путь, передаваемый затем в `12699950`, начинается как CString-copy
из **selected object+2ce8**: `124a9f00 → 124a9f0a`. Сам объект возвращает
`124a9da0`, чья cached ветвь уже связана с PLC_KBase. Это уточняет локальный
источник пути, но не доказывает отсутствие изменений содержимого файла внутри
`12677730` и не завершает аудит всего workflow. Fallback+188 ещё не типизирован.

Дополнительно проверен именованный `PLC_KBase::GetProgramOffsetInBinaryFile`
(`121c9b96`): возвращает0 либо `0x1a` при descriptor+44 &0x3c.
Единицы результата и его связь с базами30/100 здесь не установлены.
Приравнивать эти значения или использовать accessor как готовый extractor нельзя.

После возврата в `124c597c` есть дополнительные файловые проверки, в частности
`12686110` (сырой отчёт назван `file-send-entry-ghidra.json`). Он не объявляется
доказанным sender: его разбор показывает чтение и проверки данных, но не заменяет
уже исследованную цепочку `CDMDownloadProgram`/service532.

## Проверки и следующий шаг

`verify-obj-flow.py` дал **64/64**: source hashes отчётных входов, завершение
декомпиляции, ключевые assembly инструкции, именованный export, Write thunk,
хеши/word5 двух compiler N1 и четыре синтетических расчёта смещений.
Ни vendor-код, ни преобразование не исполнялись. Сети не было, проекты не менялись.
Бэкенд не менялся; `WriteQualified=false`. `.37` только чтение, `.36` offline.

Далее: получить сохранённый образец самого OBJ либо проследить его writer,
сопоставить его заголовок и полезную область с нашим N1; установить descriptor
bit20 для целевых профилей и завершить ветвь fallback+188. Для обычного N1
в первую очередь нужен полный путь без extended protection, а не реализация
защищённого преобразования по одному статическому фрагменту.
