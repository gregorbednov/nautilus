# CJ1: офлайн-аудит передачи и остановка после сбоя

18 ноября2026 года. Продолжение [плана передачи](omron-um-service-fields-and-write-plan.md)
и [различающих примеров финализации](omron-um-finalization-boundaries.md).
Добавлена модель анализа сохранённых данных и CLI. Обращений к ПЛК,
загрузки vendor DLL, изменения режима или исполнительных механизмов не было.
Все новые обмены и примеры обратного чтения в этом этапе — **синтетические**.

## Что реализовано

`transfer.NewProgramWriteAudit(image, blockBytes)` строит частный canonical
план и сохраняет собственную копию исходного N1. Пользователь не передаёт
изменяемый ProgramPlan в качестве доверенного плана. Его последующие изменения
исходного буфера, запроса, ответа или Snapshot не меняют состояние аудита.

| Состояние | Значение в сохранённой последовательности |
| --- | --- |
| ready | Можно проверить следующую записанную попытку с ожидаемыми байтами |
| awaiting-ack | Есть одна попытка; следующий блок не предлагается |
| awaiting-readback | Все блоки имеют точные ACK; совпадение образа ещё не проверено |
| source-bytes-matched | Последнее обратное чтение побайтно совпало с исходником |
| stopped | Ошибка; аудит не возобновляется и не предлагает повтор |

Состояния относятся к данным журнала, а не к режиму или фактическому состоянию
CPU. `source-bytes-matched` не подтверждает адрес устройства, время чтения,
исполнение, настройки или аппаратную приёмку. События после этого сравнения
делают последовательность некорректной и переводят аудит в stopped.

`RecordAttempt` сверяет **весь** payload очередного блока, включая данные,
смещение, количество и final bit. `RecordResponse` использует прежнюю строгую
проверку0307: ровно тот номер программы, offset и полный count. Частичные,
чужие, повторные ACK, ошибки PLC и отличающиеся запросы не увеличивают прогресс.
Даже отрицательный ответ CPU не принимается за доказательство неизменности UM.

`RecordFailure` останавливает аудит после записанного отказа/тайм-аута.
Поздний ACK, повтор блока и новое обратное чтение не возобновляют stopped.
Метода Reset/Resume нет; откат не выполняется. NextOffsetBytes — граница
подтверждённого префикса плана, не разрешение продолжить запись с этого места.

`uncertainWrite` консервативно остаётся true после любой записанной попытки,
пока вся последовательность не закончится точным сравнением. Это не флаг
транспортного тайм-аута; ход последовательности определяется State.
`reconciliationRequired` отмечает остановку после попытки записи. Признаки
`networkAccess`, `routeSIDVerified`, `hardwareQualified`, `writeQualified` и
`rollbackPerformed` не становятся true ни в одном результате этой модели.

## Обратное чтение и восстановление

`RecordReadback` допускается только после всех точных ACK. Сравнивается полная
длина и каждый байт. Различия только в служебных словах0/1/4 классифицируются
отдельно, но тоже останавливают аудит: финализация CPU пока не квалифицирована.
Неизвестные поля2/3/5, другой размер, изменённое тело и лишние bytes не удаляются,
не маскируются и не принимаются как padding.

`InspectReadback` разрешён и после ошибки. Он только сравнивает предоставленные
bytes с исходником и не изменяет состояние. Даже если файл полностью совпадает,
неопределённость и stopped не снимаются. CLI выводит такой результат отдельно
как `readbackInspection`, сохраняя ошибку и ненулевой exit code. Это позволяет
анализировать последующее чтение без автоматического возобновления записи.

Пакет не выполняет само чтение, не подтверждает источник файла и не создаёт
резервную копию. Полное восстановление требует отдельного сценария с текущим
состоянием CPU, проверенными backup/settings/data и разрешением оператора.
Один opaque UM не заменяет полную резервную копию установки.

## CLI и формат журнала

```sh
naut omron audit-program-write [-readback FILE] IMAGE TRACE.json
```

Журнал имеет поля `schemaVersion:1`, обязательный `origin` synthetic/retained,
`imageSHA256`, `blockBytes` и массив `events`. Origin лишь заявлен автором
журнала; CLI не удостоверяет его. Хеш должен совпадать с полным IMAGE.

События: `attempt` и `response` с `payloadHex`, либо `failure` без данных.
Запрос не включает FINS header/command; ответ включает command/end code,
но не FINS header. Проверка маршрута, SID и привязки к устройству остаётся
внешней задачей. Сырые PCAP/полные кадры этим форматом не объявляются проверенными.

Пределы: trace40MiB, N1/readback16MiB, число обрабатываемых событий не более2*blocks+1,
payload до1004 bytes. Массив событий читается по одному элементу, без создания
массива всех декодированных событий. Неизвестные поля/виды, неправильный hex,
превышения и несвязанный хеш отвергаются. Пути читаются только из явных аргументов
CLI; адресов подключения, execute, изменения режима и автоматического rollback нет.

Аудит заканчивается на первой протокольной ошибке. `eventsProcessed` указывает
проверенный префикс; оставшаяся часть не удостоверяется. Повреждённый формат
входа не публикуется как валидный отчёт. Конец неполного журнала сам по себе
не доказывает транспортный тайм-аут: выводится состояние ожидания и ошибка
неполноты. Без точного обратного чтения exit code остаётся ненулевым.

Два включённых примера построены независимо на Python по схеме payload и
явно помечены synthetic. Они никогда не отправлялись и не являются аппаратными
наблюдениями:

```sh
naut omron audit-program-write -readback omron/compiler/testdata/n1-no-fb-cj1h-h.n1 omron/compiler/testdata/n1-no-fb-cj1h-h.n1 omron/transfer/testdata/program-audit-synthetic.json
naut omron audit-program-write -readback omron/compiler/testdata/n1-no-fb-cj1h-h.n1 omron/compiler/testdata/n1-no-fb-cj1h-h.n1 omron/transfer/testdata/program-audit-synthetic-timeout.json
```

Первый возвращает0 только в смысле офлайн-сравнения bytes. Второй возвращает1
и stopped, хотя диагностический readbackInspection.Exact=true.

## Проверки и оставшаяся работа

Проверены прерывания на каждом из трёх блоков, неверные/частичные ACK, повтор,
нарушение порядка, изменение данных запроса, неполные и отличающиеся readback,
служебные слова, предел размера и независимость буферов. Готовый CLI прошёл
девять явно синтетических сценариев: полный обмен; ACK-only; missing ACK;
тайм-аут; чтение после тайм-аута; правдоподобное изменение0/1/4; частичный ACK;
изменённый запрос; лишнее событие. Успехом стал только полный точный сценарий.

Далее нужны CPU/unit/capacity preflight, привязка к реальному маршруту/SID,
подтверждённые backup/settings/initial data и отдельно спроектированный сетевой
клиент. Эта модель не является разрешением на стендовую запись. Действующая
установка остаётся только для чтения; деактивация механизмов сейчас не нужна.
