| R0-04 | P1 | Исследовательские доказательства и их связи зависели от абсолютных путей локального research | Добавлен версионируемый переносимый манифест, сжатые точные логи и воспроизводимые рецепты источников |

R0-01 проверяется короткими identity/status ответами, неизвестным режимом,
неверной длиной памяти, недопустимым битовым значением и неверными блоками UM.
Локально ошибочный запрос и корректный PLC end code сохраняют работоспособность
сессии. Публичный `Call` остаётся низкоуровневым обменом; его произвольные
пользовательские payload требуют соответствующей семантической проверки.

## Переносимый реестр доказательств

Инструмент: [oracle](../../tools/omron-research/oracle/README.md).
Манифест: [manifest.json](../../tools/omron-research/oracle/testdata/manifest.json).
Исходные проекты не дублируются: полные CXP/CXT каждого случая воспроизводятся
из существующей исходной фикстуры и точной замены одной цепочки с проверкой
обоих SHA-256. Неизвестные поля и графические FB остаются в проекте.

| Случай | Источник | Связь бинарного файла с записью | Ограничения |
| --- | --- | --- | --- |
| CJ1H baseline | Рецепт воспроизведён; выбор исходника подтверждён оператором | Ранний внешний файл; профиль и результат возврата наблюдались, файл скопирован вручную | `captureComplete=false`, `binaryBindingVerified=false`; точный observer того запуска не сохранён |
| CJ1M baseline | Рецепт воспроизведён; выбор исходника подтверждён оператором | Полный файл в потоке событий после успешного возврата; CPU21 наблюдался при инициализации | Идентичность загруженного исходника в процессе не измерена |
| CJ1M input-bit | Рецепт воспроизведён; выбор исходника подтверждён оператором | Полный файл в потоке событий после успешного возврата; CPU21 наблюдался при инициализации | Та же граница идентичности источника |

Для всех случаев фактическая hardware unit version неизвестна, аппаратная
квалификация — false. Unit Ver.4.0 подтверждается логами проверки базовых
проектов только как настройка проверки программы. Верификатор не принимает
«100 errors» за «0 errors» и отвергает неоднозначные многопроцессорные логи.

Воспроизведены два точных сравнения: идентичность базовых N1 обоих CPU и
изменение ровно байта 3283 (`00 → 0F`) в input-bit. Эти факты не квалифицируют
общий кодировщик операндов или всю палитру инструкций.

Валидатор отклоняет потерянные/повторные последовательности, смену PID,
непарные операции, файл после неуспешной компиляции, чужой thread/operation ID,
stderr, ошибки observer, dropped events и неполное завершение. Новые записи
используют явный `compileSequence`; старые сохраняют маркировку `thread-order`.
Хеши проверяют целостность данных, но не аутентичность их производителя.

## Выполненные проверки

На текущем Windows-стенде прошли:

```text
go test ./omron/... ./tools/omron-research/... -timeout 90s
go test ./cmd/naut -run Omron -timeout 90s
go vet ./omron/... ./tools/omron-research/...
go build -o bin/cj1-oracle.exe ./tools/omron-research/oracle
cj1-oracle verify -root .
```

Дополнительно проверены синтаксис PowerShell и обработка сохранённой записи
через launcher: корректный replay принят; replay с ошибкой инжектора отклонён,
сырой журнал сохранён, принятые бинарные файлы не созданы. После добавления
operation ID новый live capture с F7 ещё не выполнялся.

В production-пакетах `omron` не найдены вызовы `os/exec`, загрузка vendor DLL
и обращения к Ghidra/Frida/COM. Исследовательский launcher и Go-аудитор отделены
от production-пути. Наличие переносимых эталонов позволяет проверять их без
доступа к локальному Windows research.

Добавлен [Linux workflow](../../.github/workflows/omron.yml): после подготовки
Go-модулей он выполняет offline build/test/vet, проверяет корпус, запускает
race и ограниченный fuzz, выполняет ARM64 cross-build. Этот workflow локально
не исполнялся и не публиковался; его добавление не означает успешный Linux CI.
Исполнение на Linux ARM64 также остаётся отдельной незакрытой проверкой.
