# CJ1: отправка одного блока0307 и локальная проверка возврата

18 ноября 2026 года. Продолжение [проверки backup](omron-cj1-program-backup-review.md).
Добавлен Go API `fins.Client.WriteProgramBlock(ctx,payload)`. Это явно изменяющая
операция нижнего уровня. На настоящих ПЛК она в этом этапе не вызывалась:
только localhost TCP и net.Pipe; .37 и .36 не опрашивались. CLI-загрузчика нет,
онлайн-команды CLI остаются читающими. Vendor-код не исполнялся.

## Контракт блока

Payload задаётся явно: FFFF/program, BE32 byte offset, BE16 byte count с final
bit15 только в запросе, затем bytes. `transfer.ValidateProgramWriteRequest`
выделен из прежнего ACK-валидатора; проверяет размер4..996, выравнивание4,
полное соответствие count/длины, FFFF и отсутствие переполнения next offset.
Он не валидирует весь N1, порядок блоков, модель CPU или разрешение записи.
План полного образа по-прежнему формируется `PlanProgramWrite`.

API ограничивает длину до копирования и сохраняет собственный snapshot запроса.
Изменение исходного буфера вызывающим кодом не подменяет ожидаемый ACK.
`ProgramWriteBlockLimit` возвращает996 для обычного Ethernet transport и528
для имеющегося Host Link encoder. У Host Link FINS request ограничен550 bytes;
после12-byte prefix и8-byte параметров остаётся530, с выравниванием —528.
Отрицательная/слишком малая capacity даёт0 без integer overflow. Это предел
формирования запроса, не утверждение о готовности CPU или serial-стенда.

Ответ проверяется внутри того же mutex, что и обмен request/response:
существующий FINS validator сверяет маршрут, SID, команду и end code; затем
общий ACK-валидатор требует точные FFFF, offset, полный count и размер ответа.
Проверенный successful prefix восстанавливается только для повторного
использования валидатора retained response body; неподтверждённые поля не
синтезируются как факт получения ACK. Echo final bit в count не принимается.

Возвращается только `ProgramWriteACK`. `FinalRequested` описывает запрос,
а не завершение финализации/flash/исполнения на PLC. Успешный ACK не является
сравнением readback, аппаратной квалификацией или доказательством deployability.

## Остановка после отказа

Transport error, EOF, SID/route/command mismatch, неправильный/частичный ACK
и ненулевой PLC end code закрывают клиент и делают сессию непригодной для
следующих запросов. Это атомарно относительно других обменов данного Client.
Для0307 действует также через raw `Call`: действительный end-code error не
позволяет продолжить в той же сессии. Typed ACK при любой ошибке нулевой.

Обычные чтения не изменены:0306 может обработать1104 уменьшением размера
читаемого блока; этот read-only fallback не переносится на запись.
Отказ PLC не считается доказательством неизменности UM. Повторов, reconnect,
resume, нормализации служебных слов и автоматического восстановления нет.
После неопределённого исхода нужны отдельное осознанное подключение для
диагностики и процедура согласования состояния, а не продолжение с NextOffset.

Локально неправильный запрос, превышение capacity и контекст, отменённый до
начала обмена, не обращаются к transport и не портят здоровую сессию. Это
не правило для ошибки отмены уже выполняющегося обмена: тот исход неопределён.

## Проверка

На fake transport проверены точный ACK, владение payload, неверные программа,
offset/count, лишние bytes, final bit, SID, route, command, PLC end code и EOF.
Каждая ошибка после обмена даёт ровно1 attempt/close, нулевой ACK; следующий
write и Identity не достигают transport. Проверены локальные ограничения,
pre-cancel, nil client и крайнее отрицательное значение request capacity.

Отдельный localhost TCP server проходит node handshake и требует правильные
назначенные nodes и последовательный SID. Выполнен цикл:

1. Чтение synthetic PROGRAM status.
2. Передача2624-byte минимального native N1 тремя блоками и полный readback.
3. Явная передача исходного4592-byte native N1 пятью блоками и второй readback.

В этом тесте candidate — `compiler/testdata/n1-no-fb-cj1h-h.n1`, original —
`um/testdata/cj1h-baseline.n1`. Это compiler fixtures, не2716-byte live backup .37
из предыдущего этапа.

Оба readback совпали полностью, включая изменение длины. Server только копирует
opaque bytes и не моделирует CPU finalization, защиту, память/выходы или mode
commands. Поэтому проверен возврат bytes в mock, **не восстановление настоящего
контроллера**. Отдельный TCP-тест принимает request и закрывается без ACK:
клиент не повторяет и не подключается заново.

На net.Pipe проверен реальный FA/Host Link encoder при528 bytes: request count
8210 и response count0210, включая FCS и SID. Serial port не открывался.
Прошли все10 Omron packages, Omron CLI tests и go vet; после добавления этого
граничного frame-теста дополнительно прошёл весь пакет fins. Предыдущие static
corpora и ACK/audit tests остались зелёными.

Материалы: `research/hardware/20261118-cj1-0307-block-sender-01`, исходники,
команды/журналы, fixture hashes и manifest SHA-256. Пакеты production используют
Go; новые tests не требуют CX-One, vendor DLL, Python или доступа к ПЛК.

## Что нужно до первой аппаратной пробы

Блоковый mutex не делает полную передачу атомарной и не исключает запросы
между блоками. Координатор должен владеть выделенным клиентом и контролировать
всю последовательность: точный target/route, свежие raw identity/status,
PROGRAM, scoped backup и его связь с исходным UM, рецепт кандидата и нормальное
право доступа без force. Эти условия WriteProgramBlock сам не проверяет.

Далее реализуется координатор и процедура возврата: новый read-only сбор перед
пробой, явный переход в PROGRAM, кандидат/readback, отдельный возврат исходных
bytes/readback и только затем разрешённое возвращение исходного режима.
Исполнение кандидата не требуется для первого измерения финализации.
При ошибке flow останавливается, без автоматического перехода в RUN или
подстановки догадок о service words. Backup scope/settings/data, реальные ACK,
CPU финализация и восстановление остаются неквалифицированными.

Подтверждение оператора об изоляции CJ1H/.37 уже учтено; повторное общее
подтверждение отключения механизмов для этого стенда не требуется. Для CJ1M/.36
оно не действует. Ни hardwareQualified, ни writeQualified в существующих
планах/preflight/audit от появления этого API не повышаются.
