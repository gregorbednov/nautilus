# CJ1: выделенная сессия передачи программы и явного возврата

18 ноября 2026 года. Продолжение [0307 block sender](omron-cj1-0307-block-sender.md).
Добавлен экспериментальный Go API `commission.ProgramSession`. Проверялся только
на localhost TCP; настоящие .37/.36 не опрашивались, vendor-код не исполнялся.
CLI download отсутствует. Управление режимом, доступом и защита не реализованы
этим API; PROGRAM и исключительный доступ к контроллеру обеспечивает вызывающий.
Отчёты offline preflight и сохранённый JSON не становятся разрешением записи.

## Что выполняет API

`NewProgramSession(client, config, journal)` принимает точный TCP peer, полный
ожидаемый raw0501, поддерживаемую модель, N1, размер блока и результат реальной
локальной пересборки `VerifiedImageBuild`. Проверяются proof/model/candidate,
reported capacity и маршрут напрямую к CPU (network0/unit0). Конструктор
передаёт владение соединением: исходный Client больше не может отправлять
команды или закрывать соединение; последовательность SID сохраняется.
Это исключает перемежение через старый дескриптор, но не доступ других
приложений/соединений к ПЛК. TCP peer и rawCPU не являются аутентификацией.

`Prepare(ctx)` выполняет identity/status, два отдельных полных чтения0306,
повторные identity/status. Требуются PROGRAM0, отсутствие fatal/nonfatal,
совпадение всего ожидаемого CPU DATA, стабильность всего status DATA, два
одинаковых разбираемых N1 и проверка размера. Исходник остаётся приватной
копией в памяти. Journal получает отдельные копии; его изменение переданных
срезов не может изменить будущую программу возврата или кандидата.

`WriteCandidate(ctx)` разрешён однократно после Prepare. Перед первой0307
снова проверяются CPU/PROGRAM/errors и точное совпадение текущего UM с backup.
Каждый `write-attempt` синхронно сохраняется до отправки блока. ACK проверяется
Client по route/SID/command/end и всей длине/offset/count, затем записывается
в журнал. Offline audit получает производное тело проверенного ACK; это не PCAP.
После всех ACK сохраняются сами байты0306 readback, вновь проверяется
CPU/PROGRAM/errors и требуется совпадение каждого байта. Отличия service
words0/1/4 диагностируются, но останавливают операцию. Сеть закрывается.

`ReturnOriginal(ctx, freshClient)` — отдельное явное действие. Оно доступно
только после хотя бы одной попытки отправки кандидата и требует другого
пригодного TCP Client с тем же peer и destination tuple; новый source node
допустим после handshake. Проверяются rawCPU/PROGRAM/errors. Отправляется
исключительно приватный исходник из Prepare, произвольный UM передать нельзя.
Запись/ACK/readback используют тот же строгий порядок. Частично изменённый
текущий UM не обязан разбираться перед этим явным восстановлением.
Операция возврата однократная: после её начала повторного запуска нет.
Ошибка привязки перед передачей владения не потребляет эту попытку.

Любая ошибка подготовки/проверок/сети/журнала/readback переводит сессию в stopped
и закрывает соединение. Нет автоматического reconnect, retry, resume, rollback,
RUN, снятия защиты или альтернативного0317. Остановленный audit кандидата
не возобновляется даже при успешном отдельном возврате. `Close` отзывает
возможность дальнейших действий; уже подтверждённое совпадение исходных
байтов остаётся в Snapshot. Методы сериализованы, Close ждёт текущий метод;
для прерывания I/O нужно отменить переданный context.

## Файловый журнал

`NewFileProgramJournal(path)` создаёт только новый каталог в существующем
родительском. Готовый каталог не перезаписывается. В нём:

- `candidate.n1`, `original-1.um`, `original-2.um` — исходные байты;
- `observations.json` — before/after raw identity/status, binding и build report;
- `prepared.json` — SHA-256/длины файлов, programOnly=true,
  fullControllerBackup=false; записывается последним;
- `events.jsonl` — последовательные guards, запросы, проверенные ACK,
  readback bytes в base64, сравнения, явный возврат и причины остановки.

Каждый файл создаётся эксклюзивно; запись завершает File.Sync и Close.
Каждое событие тоже Sync/Close до возврата успеха. Переносимость сохранения
метаданных каталога при внезапном отключении питания не квалифицирована.
После ошибки файловый журнал навсегда блокируется: исправление диска не
возобновляет этот объект. Поэтому при отказе самого журнала встроенный возврат
через него тоже недоступен: потребуется отдельная внешняя процедура восстановления
по сохранённым материалам. Загрузки журнала как live permission/resume нет.
Частичные файлы сохраняются для разбора; наличие prepared.json после ошибки
не доказывает успешной подготовки и не разрешает возобновление.
Полный source/settings рецепт следует сохранять отдельно: build report хранит
хэши рецепта, а не его содержимое.

## Что подтверждено и что дальше

Локальный TCP peer копирует непрозрачные bytes и не моделирует CPU. Проверен
кандидат2624 bytes (3 блока996/996/632), затем явный возврат mock-исходника4592
bytes (5 блоков). Этот исходник — fixture, не текущий живой backup2716 bytes.
Проверены запрет записи до подготовки, RUN/CPU errors/identity conflicts,
несовпадение пары, изменение UM после backup, отмена context, ошибки сохранения
backup/attempt/ACK/readback, потеря ACK, service-only mismatch, посторонний peer,
однократность неуспешного возврата и неизменность приватных данных.
Проверены сохранённые original/readback bytes и невозможность возобновить
повреждённый файловый журнал. Всего добавлено9 top-level Go tests с25 subcases.

Все10 Omron packages, Omron CLI tests и go vet проходят. Эти результаты
подтверждают механику координатора, а не приём программы настоящим CPU.
HardwareQualified, WriteQualified, RestoreQualified и FullControllerBackup
всегда false. ProgramBytesReconciled означает только точный readback исходного UM.

До аппаратного опыта остаются реализация/проверка mode/access lifecycle,
protection/0307-vs0317 и target profile/unit-version/finalization, полный backup
вне программы, операторская процедура и аппаратная проверка возврата/исполнения.
Последним сообщением оператор подтвердил сетевую доступность и отключение
исполнительных механизмов для обоих CJ1H/.37 и CJ1M/.36; остались светодиоды
и прочие незначащие нагрузки. Вопрос изоляции закрыт для обоих стендов,
прежнее исключение CJ1M/.36 из стендовой подготовки отменено. Это сообщение
не заменяет технические проверки и аппаратную квалификацию.
Следующий этап разработки — mode/access lifecycle с такими же локальными
проверками ошибок, затем подготовка конкретного сценария опыта на CJ1H.

Raw `research/hardware/20261118-cj1-program-session-02`: 12 files,
SHA256SUMS `40d38d7d9eb0343795d6c25def6db49a839fcff7ee06c3030cb733334a3ca6a5`. Localhost only; no PLC traffic.

Последующее исследование: [mode/access wire API](omron-cj1-mode-access.md)
уже реализованы отдельно от координатора.0C03 освобождает право любого
владельца; Close не подтверждает освобождение, fresh client не наследует
старый access ACK. ProgramSession ещё требует интеграции control шага/журнала
и сохранения нужного соединения до явного завершения access lifecycle.

19 ноября: новый [controlled вариант](omron-cj1-controlled-session.md) интегрирует
явные control шаги и сохраняет соединение после matched readback до Finish.
Прежний NewProgramSession остаётся совместимым legacy путём. На CJ1H подтверждён
mode-only цикл без0307; после явного подтверждения аналогичный опыт CJ1M
также [завершён успешно](omron-cj1m-mode-only-2026-11-19.md).
